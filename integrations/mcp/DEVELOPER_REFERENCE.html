MCP Developer Reference

Implementation guide for the Python/FastMCP adapter in integrations/mcp. The server exposes the SolariNet REST contract and three fixed database views to MCP clients.

1. Component boundary

The MCP server is an adapter. It translates MCP tool inputs into calls to the dashboard API or fixed read-only database operations, then converts results into JSON or compact Markdown. The dashboard API remains the authorization boundary for REST operations; the database account should independently be read-only.

Current scope: 15 read-only REST tools, 8 REST control tools, and 3 fixed database tools. Arbitrary SQL is not exposed to MCP callers.

Control REST (8)

Control tools call POST operations and are side-effecting. They use the configured bearer token; API role checks remain authoritative. To start streamable HTTP, set SOLARINET_MCP_TRANSPORT=streamable_http; the adapter maps this project value to the FastMCP 1.x transport name streamable-http and applies SOLARINET_MCP_PORT to the SDK listener settings.

python -m solarinet_mcp --check prints configuration status and registered tool names without opening a listener or connecting to the API/database. It does not print credential values.

5. Security and trust boundaries

  • HTTP exposure: the tested FastMCP 1.30.0 runtime defaults to 127.0.0.1; this project does not implement MCP-client authentication. Keep HTTP local or put remote access behind an authenticated, access-controlled tunnel or proxy. Do not expose the listener directly to an untrusted network.
  • REST writes: MCP annotations help clients distinguish read-only and side-effecting tools, but annotations are not authorization. The dashboard API's bearer token and RBAC checks enforce access.
  • Database reads: no MCP tool accepts SQL. Internal query validation is defense-in-depth; it is not a full SQL parser. Use a MariaDB account granted only the needed SELECT privileges.
  • Transport security: REST TLS verification defaults on. Disabling it weakens server identity checks and is intended only for controlled testing.
  • Secret handling: supply tokens and database passwords through the process environment/secret manager, never source files or command-line arguments. Do not include real values in diagnostic output.

6. Errors, bounds, and execution model

The REST client requires the dashboard's JSON envelope with a data member, maps API error envelopes and HTTP 401/403/404 responses to concise tool errors, and reports timeout or transport failures explicitly. The database driver is synchronous, so queries run in a worker thread to avoid blocking the async tool loop.

The DB guard strips comments, accepts a single SELECT/WITH statement, rejects stacked statements and file export clauses, checks referenced tables against an allow-list, binds values as parameters, and limits result rows (default 100, hard maximum 1000). These checks reduce accidental exposure; the database grant is the enforcement boundary if code or parser assumptions fail.

Tool inputs use Pydantic models with extra fields forbidden and explicit bounds where relevant. Response formatting is JSON for machine use or compact Markdown for readable summaries. Tests inject HTTP transports and database runners rather than reaching production services.
