Chapter 1

About this manual

Who this is for

This manual is for anyone who changes SolariNet: its C daemons, its PHP dashboard, its two databases, its sync and alert daemons, its provisioning tooling or the way it is released onto xenon. It explains how the system is put together, how each part talks to the others, and where the sharp edges are. It is not an operator's guide; the User Manual covers day-to-day use, and the API Expansion Manual covers adding routes and integrations.

It replaces docs/SolariNet_Developer_Reference.html. Every claim here was checked against the repository at main a28bdf2 or against the running system on 2026-11-03, rather than copied from older documents. Where an older document disagrees with what is true now, Appendix B records the disagreement.

Conventions

  • SoR means the system-of-record database sor on cesium. Monitoring DB means the solarinet database on xenon. They are separate servers with separate schemas and separate migration trees.
  • Relative paths (src/, dashboard/, deploy/…) are repository paths; absolute paths (/opt, /etc, /run, /srv) are host paths.
  • Ports are written host:port or :port. All internal names are in akoria.net unless written otherwise; Active Directory is akoria.org.
  • Passages on SoR migration 037 behavior are marked in the source for checking against the merge; they describe it as current.

Chapter 2

System context

What SolariNet is

SolariNet is the monitoring, inventory and provisioning system for the SolariNet homelab, a self-hosted network of about 40 named hosts across eight logical networks. It does four jobs:

  • Monitor. Agents on enrolled hosts report health; monitor agents probe services; a server ingests both, raises alerts and keeps history.
  • Record. A system-of-record database (the SoR) holds the intended state of the network: entities, addresses, interfaces, DNS, functions, inventory and provisioning catalogs, each row stamped with where it came from.
  • Apply. Changes to the SoR are captured and pushed out to the systems that act on them: BIND zones and Samba Active Directory.
  • Provision. Bare-metal hosts are network-booted, installed, enrolled and brought to a software stack with Ansible.

The operator works through one web dashboard, used mostly on an iPad. An LED status panel on lithium shows the same state at a glance.

House rules that shape the code

These come from the project instructions and the operator standard, and they explain choices that look odd from outside:

  • The application is standard C. Every daemon on the monitoring path is C with Makefiles and CMake. Python is used for glue that is not on the monitoring path.
  • No server-side JavaScript, ever, and no build step where none exists. The dashboard UI ships its JSX source; the browser compiles it.
  • camelCase for variables, functions and structures in C and PHP alike, even where the language community uses snake_case. Database columns stay snake_case.
  • Prefer functions to objects. The C core uses opaque handles; PHP classes are mostly static namespaces (Auth, Policy, Sor).
  • Comment intent. Each program, function and non-obvious control structure states its purpose, input and output.
  • A socket accepting a connection is not health. Learned from the 2026-07-07 cesium incident, where Forgejo returned errors for about 26 hours while a bare TCP check stayed green. Health checks must exercise the application.

DNS

akoria.net is authoritative on BIND. xenon is the primary; radium, chlorine and steel are secondaries. The SOA observed on all four was xenon.akoria.net. hostmaster.akoria.net. 2026110302 3600 600 604800 300. observed The NS set published in the zone is xenon, radium and chlorine; steel transfers the zone but is not listed as NS.

Zones are generated, not hand-edited. netdb/gen-zones.py --source sor renders forward and reverse zones from the SoR; the dns-release engine (deploy/dns-release) installs each render as a new generation, validates it, swaps it in, checks the served SOAs and keeps a journal so a bad generation is rolled back (Chapter 8). The forward zone is transferred to 10.1.0.10, 10.7.0.10 and 10.0.0.11; reverse zones to 10.7.0.10 and 10.0.0.11. The live transfer lists are in /etc/solarinet/dns-release.json. solari-dns-secondary-refresh (a timer and a path unit on xenon) refreshes chlorine's secondary zone list when the release changes.

Service names are descriptive CNAMEs: dashboard → xenon, sso → radium, git → cesium, db → benzene, ca → chlorine, ns1 → xenon. Each service is reached by name on :443 with SNI rather than on an arbitrary port.

xenon also serves a response-policy zone built daily at 04:30 from the StevenBlack block list (solarinet-rpz-refresh.timer). akoria.org is the Active Directory DNS zone, served by Samba on radium.

A node ID is the FNV-1a 64-bit hash of "fqdn|ROLE". The server checks that the certificate CN presented on the TLS session matches the claimed source node and its approved record. The installed nng 1.x API does not expose the peer's leaf certificate, so the server cannot yet compare the stored leaf fingerprint on live connections.

Transport and delivery

PortServer socketPeer socketCarries
:7701PULLPUSHBest-effort frames: watchdog, discovery adverts, topology
:7702REPREQDurable reports (CLIENT_REPORT, MONITOR_REPORT, SURVEY_RESP), acknowledged

All three listen on tls+tcp://0.0.0.0 with mutual TLS. observed solariReporter sends durable reports over REQ to the report-ack URL (derived from the primary URL by switching to :7702, with failover to other servers). It waits for an ACK correlated to the frame's sequence number and a 16-byte session TLV (0x0105), and it requires the server certificate's CN to be server. Durable reports also carry the CRL-activation receipt TLV. If no ACK arrives, the frame goes to the SQLite spool and is replayed later with SPOOL_REPLAY set. Delivery is at-least-once; the server de-duplicates by node, session and sequence.

solariServer internals

solariServer is a single-threaded poll() loop, serverRunLoop in src/server/main.c. It never blocks on one peer.

Lease: active and standby

Several servers can share one monitoring DB. Exactly one is active, decided by a lease row (serverLease) renewed every 5 s with a 15 s TTL in one conditional UPDATE. Only the active server drains ingest (in bursts of up to 64 frames), runs the ctl queue, and answers mutating ctl verbs. A standby answers only PING, REQUEST_GET and DISCOVER_STATUS.

Configuration

server.conf sections: [identity], [bind], [tls], [ca], [lease], [db], [discovery], [ingest] and [ctl] (enforcePeer, operatorUid, dashboardUid, socketGid, helperRoot, logDir). The DB password is read only from the environment variable SOLARI_DB_PASS, set by the unit's environment file. Schema is created by migrations, never by the server: --init-db is retired.

Responsibilities

  • Ingest writes reports to the monitoring DB and updates node, health and probe state.
  • Alerting (serverAlert.c) evaluates rules, writes alertEvent rows with a disposition (suppress or publish) and PUBs them (Chapter 9).
  • Discovery and enrichment (serverDiscovery*.c, serverOui.c, serverScan.c) manage scan jobs and annotate discovered hosts. The scan input is capped at about 4,096 hosts (a /20) per job.
  • Topology (serverTopology.c) assembles LLDP and interface data from solariSnmpPoll.
  • CA signs agent CSRs on approval and issues the enrollment certificate.
  • Provisioning verbs (serverProvision.c) start helper programs for fleet install, image refresh, staging and stack apply.

The ctl socket

The ctl socket is the only way into solariServer from the same host. The dashboard uses it for every privileged action. It is an AF_UNIX stream socket at /run/solari/solariCtl.sock, observed as owner jason, group solari-ctl, mode 0660, inside /run/solari (mode 751). observed

request:  VERB key=value key=value\n        (≤ 16,384 bytes, one per connection, 2 s read timeout)
reply:    OK [key=value …]  |  ERR <code> <message>   (≤ 32,768 bytes)

The server classes each peer by SO_PEERCRED: root or the configured operatorUid is OPERATOR, the dashboardUid is DASHBOARD, anyone else is UNKNOWN. Verbs fall into three classes:

Request lifecycle

dashboard/api/index.php runs the same steps for every request:

  1. Bootstrap (lib/bootstrap.php) loads the libraries and configuration from the environment.
  2. Install the guard. $router->setGuard([Policy::class, 'enforce']).
  3. Register routes from routes/auth.php, routes.php and routes_mutations.php, which in turn include the per-area files in routes/.
  4. Session gate. Auth::requireSession() runs for every path except /api/auth/* and the two bearer-authenticated enrollment endpoints (POST /api/enrollments and POST /api/enrollments/ack). Failure is 401 unauthorized.
  5. Dispatch. The router matches method and path ({name} segments). No path match is 404 not_found; a path match with the wrong method is 405 method_not_allowed.
  6. Policy. The guard receives the matched route and the real request method, and runs before the handler: role check, then CSRF. Failure is 403 forbidden.
  7. Handler. Validates input (lib/Coerce.php), reads or writes the monitoring DB or the SoR, or calls the ctl socket, and returns through lib/Response.php.

Every response is JSON with Cache-Control: no-store: {"ok":true,"data":…,"ts":…} or {"ok":false,"error":{"code":…,"message":…}}.

Policy and CSRF

Each route declares one of four auth levels: public, session, operator or admin. A route that declares nothing gets session for GET and operator for any mutating method. Of the 194 routes in docs/authz/AUTHZ_MANIFEST.json, 6 are public, 86 need a session and 102 need an operator.

Every POST, PUT, PATCH and DELETE must pass two CSRF checks: the Origin (or, failing that, Referer) is same-origin, and the X-Solari-CSRF header equals the session's token, compared with hash_equals. The one exception is the panel-service bridge: the local panel viewer may post panel state when it sends no Origin, Referer or Sec-Fetch-Site, because it is a daemon and not a browser.

Provenance

Every SoR row that someone or something asserts carries provenance columns: source_id (→ sources), asserted_kind (human or machine), asserted_at, created_at, updated_at and, for soft deletion, deleted_at. The live sources are manual, dashboard, netdb, samba_ad, bind, forgejo, solarinet_monitor, unifi, pihole, rackwire, provisioner and scanner-ingest. observed

The rule for conflicting writes: a human assertion wins for intent fields (names, roles, criticality, lifecycle); a machine assertion wins for observed fields (MAC, last seen, firmware). Writers stamp their own source and must not overwrite a human-asserted intent field from a machine path.

Soft-deleted rows stay in the table. Uniqueness among live rows uses a generated live_flag column (1 when deleted_at is null, otherwise null) inside the unique key, so a deleted row never blocks a new one with the same natural key.

Types and conventions

  • IP addresses are native INET6. IPv4 is stored v4-mapped. Read with CAST(col AS CHAR); write with CAST(? AS INET6). INET6_NTOA on the native type and a bare INET6_ATON on IPv4 text both fail silently; INET6_ATON('::ffff:a.b.c.d') with an explicit v4-mapped prefix works, and is what the discovery reconciler uses.
  • Criticality is functions.criticality, TINYINT 1–5 with 1 the most critical, default 3, enforced by a CHECK constraint.
  • Lifecycle lives on entities.lifecycle. Retired rows are tombstoned, not deleted.
  • Edit conflicts are optimistic: a client sends back the updated_at it read; the handler locks the row (SELECT … FOR UPDATE) and returns 409 conflict if it changed.

SoR sync and messaging

Why change data capture

The SoR is the single place where intent is written. Systems that act on that intent (BIND, Samba AD) must follow it without the dashboard or any other writer having to know about them. SolariNet does this with a transactional outbox: the same transaction that changes a row writes a change record, and separate daemons turn those records into actions.

Outbox and emitter

CDC triggers on 23 tables (dhcp_ranges, dns_records, dns_zones, entities, entity_functions, external_refs, functions, function_incompatibility, interfaces, ip_addresses, networks, sources, subnets, vlans and the nine prov_* tables) insert (table_name, row_id, action) into sor_outbox. observed

deploy/sorsync/sor_emitd.py (unit sor-emit on xenon) polls the outbox and publishes each row to the durable topic exchange sor.events with routing key sor.<table>.<action> and a JSON body {outbox_id, table, row_id, action, ts}. Messages are published mandatory (except for tables listed as optional) with publisher confirms, and the checkpoint emit_checkpoint in sor_sync_state moves forward only after the broker confirms. If the emitter dies between publishing and checkpointing, the same rows are sent again: delivery is at-least-once, and consumers must be idempotent.

Chapter 9

Alerting and notification

From probe to phone

  1. Raise. serverAlert.c in solariServer evaluates alert rules against incoming reports. It writes an alertEvent row with a disposition (publish or suppress, using the 5-tier criticality and any acknowledgement) and also PUBs the event.
  2. Bridge. deploy/alertbridge/alertbridge.py polls alertEvent from a checkpoint, drops events for hosts inside a maintenanceWindow, and publishes the rest to notify.events with routing key notify.<severity>, waiting for confirms. Already-checkpointed events are never published again.
  3. Fan out. deploy/notify/notifyd.py consumes notify.events and routes each message, by severity, to the senders enabled in notify.conf.
  4. Acknowledge. The dashboard sends ALERT_ACK through the ctl socket. The status panel can acknowledge the active alarm with its ACKALARM control (Chapter 12).

The dead-man's switch

alertbridge also watches the watchers. Each cycle it computes how long ago each node last reported, from hostCurrent (clients) and probeCurrent (monitors). A node that was reporting and has been silent for more than max(120 s, 3 × its sample interval) produces one synthetic crit “stopped reporting” message; when it reports again an info recovery follows. Nodes in a maintenance window are skipped. This is the check that would have caught cesium's 26-hour silence in July.

Provisioning

From bare metal to a running stack

Provisioning takes a host with an empty disk to an enrolled SolariNet node with its software stack applied. The SoR describes what each host should be (entities, entity_functions, prov_images, prov_stacks); deploy/fleet turns that into boot files, installer answers and Ansible runs.

Network boot

The netboot tree is rendered by the fleet helpers from the SoR image and host rows (deploy/fleet/netbootlib.py owns every path and every iPXE line) and rsynced to benzene, which serves it over HTTP on nginx http://10.5.2.50:8080/ and serves the iPXE loaders over TFTP. DHCP points machines at it in one of two ways: a proxyDHCP on benzene, or UniFi DHCP options with next-server 10.5.2.50 and filename ipxe-x86_64.efi. Which one is live was not checked. unverified

The loader runs an embedded script that chains boot.ipxe, then a per-machine mac-<mac>.ipxe (stage 1), then a stage 2 menu offering the installer for the image's family (preseed for Debian, Ubuntu autoinstall through a NoCloud data source, AutoYaST for openSUSE, which installs from the upstream repository). Stage 3 is the local disk. Images are fetched and checksummed by fetch-images.sh and image-refresh.py; prov_images.os_id links each image to its distribution row in operating_systems, so reimaging a host also sets its OS in the SoR.

First boot and enrollment

The installer drops solari-firstboot.sh, which installs solariClient and writes /etc/solari/PENDING_ENROLLMENT. Enrollment then follows the token flow in Chapter 5. prov-finish.py, run by solari-prov-finish.timer on xenon, notices hosts that have finished installing and enrolled, and queues the stack apply.

STACK_APPLY and Ansible

STACK_APPLY is a privileged ctl verb, so it arrives through the ctl queue. solariServer starts stack-apply.py, which:

  1. generates the host's stack variables from the SoR with stackgen.py --from-db;
  2. inserts a prov_runs row (append-only, see Chapter 7);
  3. runs ansible-playbook playbooks/site.yml --tags stack on benzene through provlib.remote_run, which uses ssh in BatchMode, first with --check --diff and then for real;
  4. records the result on the run row.

The Ansible tree lives in deploy/fleet/ansible and is published to /srv/solari-provision/ansible on benzene by deploy/fleet/sync-ansible.sh (exit 0 in sync, 1 drift, 2 check failed). On benzene the published tree is a set of symlinks into a release. Roles: base-os, common-stack, dev-tools, directory-join, dns-secondary, shared-home, solarinet-client and stack-items. steel became a BIND secondary through the dns-secondary role in this way.

The other provisioning verbs follow the same pattern: FLEET_PROVISION → fleet-provision.sh, FLEET_IMAGE → fleet-image.sh, IMAGE_REFRESH → image-refresh.py, PROV_STAGE → prov-stage.py.

Setting SOLARI_ALLOW_UNVERIFIED_PROVISIONING=1 overrides it and is meant only for an isolated lab network. prov-store-guard.sh checks the image store on the provisioning host before helpers read or write netboot payloads.

Rules that hold the boundaries

  • PHP never holds operator authority. It may only ask; solariServer decides. Privileged ctl verbs are queued with the requesting operator's name, and the active server replays them.
  • PHP never signs. Certificates are signed by solariServer (agents) or by step-ca by hand (hosts and services).
  • No private key leaves the host that made it. Enrollment moves CSRs and certificates only.
  • Secrets live in files referenced by path: the php-fpm pool configuration, unit environment files, /etc/solarinet/, /etc/solari/. They are never written to git, logs or the SoR.
  • License keys are never stored. Inventory keeps a reference to where a license lives.
  • Destructive verbs name an operator and, for decommissioning, need a confirmation token.

Releases are named rc-YYYYMMDD-<short sha>-io; the -io suffix marks a build with the nng and mbedTLS transport. Releases are cut from main. Git work lands on Forgejo first; GitHub is a mirror.

  1. Merge to main on Forgejo; wait for CI.
  2. Apply database migrations with tools/migrate.py, SoR and monitoring separately, before the release that needs them. Migrations are not part of the release tarball's cut-over.
  3. Build, package, install and cut over.
  4. Run the verifier; check the dashboard and the alert path.
  5. If service-worker-cached files changed shape, the release must also bump CACHE_VERSION in sw.js.

Coding standards

  • C: C99, warning-clean under -Wall -Wextra -Wpedantic; camelCase; opaque handles instead of exposed structures; every function documents purpose, input and output; no allocation on hot paths without a bound; parsers fuzzed.
  • PHP: PHP 8 with strict_types; functional style; prepared statements only, with no named placeholder reused within one statement (a CI test checks this); every write in a transaction with FOR UPDATE on the rows it changes. Newer route files use snake_case helper functions; follow the style of the file you are in.
  • JavaScript: browser only, JSX compiled in the browser, no build tooling. Python: standard library where possible; daemons log, back off and reconnect on transient database or broker errors rather than crash.
  • SQL: new migrations only, never edits to applied ones; provenance on every asserted row; native INET6 for addresses.
