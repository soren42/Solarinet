Chapter 1

About SolariNet and this manual

SolariNet watches the Akoria home network and keeps its official record of systems, addresses and things owned. You use it through one web dashboard, a wall-mounted LED status panel and the messages it sends you.

1.1What SolariNet does#

SolariNet has five jobs. Each has its own part of the dashboard.

Watch

Measures every enrolled host and probes every service from several vantage points. See Chapter 3.

Warn

Turns sustained problems into alerts, messages and a panel alarm, and stays quiet during maintenance. See §3.7.

Record

Keeps the System of Record: hosts, addresses and DNS names, plus every component, location and project. See Chapter 4.

Build

Finds new hosts, enrols them, and installs or reimages machines over the network. See Chapter 5.

Run the plumbing

Shows the state of Git, the certificate authority and DNS so you can check them in one place. See Chapter 6.

1.2How the pieces fit#

You do not need this section to use the dashboard. It explains where the data comes from, which helps when something looks wrong.

  • Agents. Every enrolled host runs solariClient, which reports CPU, memory, disks, network and processes. A few hosts also run solariMonitor, which probes services on other hosts. Both connect to solariServer on xenon over mutually authenticated TLS, using a certificate issued to each host.
  • Two databases. The monitoring database, on xenon, holds measurements, alerts and rules. The System of Record (SoR), on cesium, is the authoritative list of hosts, addresses, DNS names and inventory. Both are MariaDB.
  • Change flows outward. When the SoR changes, the change is queued on RabbitMQ (on benzene). Services such as the DNS renderer then pick it up, so a host added in the SoR soon has a DNS name.
  • Alerts flow to you. alertbridge turns alert events into messages on RabbitMQ, and notifyd delivers them. Separately, the panel daemon on lithium draws health on the LED panel and sounds its alarm.
  • Sign-in goes through Akoria SSO (Keycloak on radium) or, if enabled, a local account.

1.4How to use this manual#

  • New to the dashboard: read Chapter 2, then the section for the screen you need.
  • Looking for one task: use the search box at the top. It highlights every match and filters the contents list. Press Enter to jump between matches.
  • Something is wrong: go straight to Chapter 7.
  • Unsure of a term: see the Appendix A.

Each screen section opens with a summary box: what the screen is for, how to reach it, who can change things, and how mature it is. After that come the layout, a table of controls, numbered procedures and notes for iPad and iPhone.

Chapter 2

Getting started

Sign in, learn the layout of the dashboard and find your way around. Everything in later chapters builds on this one.

2.1Signing in#

Address
https://dashboard.akoria.net from inside the network or over the VPN
Methods
Akoria SSO (the usual way) or a local account, if the server has local login turned on
Who
Anyone with an Akoria directory account. Your role decides what you can change (§2.5).

Sign in with Akoria SSO#

  1. Open https://dashboard.akoria.net. If you are not signed in, the sign-in screen appears.
  2. Select Sign in with Akoria SSO. The browser goes to the Akoria sign-in page at sso.akoria.org.
  3. Sign in there with your Akoria (Active Directory) username, and then your password, one-time code or passkey, whichever the SSO page asks for.
  4. The browser comes back to the dashboard and opens Fleet Overview.

The SSO sign-in has to be completed within 10 minutes of selecting the button. If it takes longer, the dashboard shows Invalid or expired SSO login attempt. Please try again. Select the button again.

Sign in with a local account#

Local accounts are for recovery and service use, for example when SSO is down. They exist only if the server administrator turned local login on.

  1. Type the Username and Password.
  2. Select Sign in. The button reads Signing in… while it checks.

A wrong username or password shows Invalid username or password. The message is the same for both, so it does not reveal which accounts exist. Each username can be tried at most five times from one address in any 15 minutes. After that, sign-in is refused until the oldest attempt is 15 minutes old, even with the right password.

Passkeys and one-time codes#

Second factors and passkeys belong to your Akoria SSO account, not to the dashboard. You manage them in the Keycloak account console:

  1. Open https://sso.akoria.org:8443/realms/akoria/account/ and sign in.
  2. Open Account security, then Signing in.
  3. Under the passkey or authenticator-application heading, choose to set one up and follow the prompts. On an iPad or iPhone, the passkey is saved to iCloud Keychain.
Not verified

The menu names above are Keycloak's standard account-console labels. This manual did not check whether the Akoria realm requires a second factor, or which factors it offers. If the account console differs, follow what it shows.

Sessions and signing out#

  • Idle timeout: 30 minutes with no requests ends the session. The dashboard polls every 10 seconds while a tab is open, so an open tab stays signed in.
  • Maximum length: 8 hours for a local account, 1 hour for an SSO session. After that you sign in again.
  • Role refresh: for SSO users, the server rechecks your directory groups about every 60 seconds. If that check fails, the session continues as a viewer until you sign in again.
  • Signing out: open the profile chip at the top right and select Log out, or press ⌘K and choose Log out.
Shared devices

Logging out of the dashboard probably does not end your Akoria SSO session inferred. Selecting the SSO button again may sign you straight back in. On a shared device, also sign out of the account console.

2.2Installing on an iPad or iPhone#

The dashboard is a web app that can live on your Home Screen and open full screen, without Safari's toolbars.

  1. Open https://dashboard.akoria.net in Safari and sign in.
  2. Tap the Share button, then Add to Home Screen, then Add.
  3. Open SolariNet from the new Home Screen icon. It opens full screen.
iPad and iPhone

The installed app does not store your data for offline use. Without a connection it shows sample data under a DEMO DATA banner (§2.6). It does not send push notifications; alerts reach you through the channels in §3.9.

Command palette#

The command palette is the fastest way to get anywhere.

  1. Press ⌘K (Ctrl K on a PC) or /, or select the search pill.
  2. Type part of a page name, an action or a host name. Results are grouped as Navigate, Actions and Jump to node.
  3. Use the arrow keys and Enter, or tap a result. Esc closes the palette.

The Actions group switches Fleet Overview between Heatmap, Table and Cards, runs Survey entire fleet now, toggles the theme and logs you out. Jump to node lists problem hosts first, then up to 40 healthy ones. You can match a host by name, role, IP address or segment.

Known issue

The / shortcut also fires while you are typing in some multi-line boxes and drop-down menus. If the palette opens unexpectedly, press Esc and keep typing.

2.5Roles: viewer, operator, admin#

Your role is set when you sign in. It does not depend on which device you use.

RoleCanHow you get it
viewerSee every page and every record. Cannot change anything.Default for every SSO user.
operatorEverything a viewer can, plus every change on every screen. Examples: acknowledge alerts, schedule maintenance, edit inventory, adopt hosts, deploy, reimage, control the panel.Membership of an operator group named in the server's SSO settings.
adminEverything an operator can, plus permanent deletion (Purge) of a system's tombstone.Membership of an admin group (by default Domain Admins). Local accounts are admins unless configured otherwise.

The server checks every change: by default, signed-in users may read and operators may write. Some screens also hide or disable controls you cannot use. Others show them anyway. If you select one, a message appears: This action requires an authenticated operator role. Appendix B lists each action and the role it needs.

Queued actions

Some actions are carried out by the server daemon rather than the web API: survey, push config, re-push, deploy, sign and stage. If the daemon has not answered within about 4 seconds, the dashboard reports the action as queued. It will still run. If the daemon cannot be reached at all, you see control_unavailable and nothing is queued.

Reading a tile#

Tile colour is health: Up, Degraded (over a tolerance), Down (no data or unreachable) and Unknown (not yet reported). Stale tiles, from hosts that have stopped reporting, are dimmed and their tooltip says stale. Critical systems sort first in each segment.

Pool cards#

Pools are named groups of systems, such as DNS or Core infra. When pools exist, a strip of pool cards appears above the fleet view. Each card shows the pool's health. Select a card to open Systems. An operator can delete a pool from its card. Its members move to Unassigned, pool 1, which cannot be deleted. To create pools, see §3.4.

iPad and iPhone

Long-press a tile to see its tooltip. On an iPhone the heatmap tiles are small; the Table or Cards view is easier to read.

Retiring a host#

  1. On the host's detail page, select Retire.
  2. Read the dialog. The host leaves the active roster: no more samples are expected, its open alerts are cleared, and it moves behind the Retired filter. Nothing on the host itself is touched.
  3. Select Retire node.

Known issue

On this page, Survey now and Push config currently survey the whole fleet, not just this host. That is harmless, but it is not what the label says.

3.3Criticality tiers#

Criticality tells SolariNet how much a system matters. It changes alert severity, who gets notified and whether the LED panel alarms. Set it on any Node, System or Service detail page with the five-button selector. The behaviour of the selected tier is shown under it as you choose.

TierLabelBehaviour, as the dashboard states it
0IgnoreStill monitored and graphed. Never raises an alert.
1LowAlerts cap at warning, and nothing is ever notified.
2NormalStandard alerting and notification. This is the default.
3HighCritical alerts notify, and the status panel alarms with them.
4VitalEvery alert fires critical, notifies at once, and holds the panel alarm while this is down.

Lists show a tier chip only for systems not at Normal, so the chip means "weighted differently". A service inherits its parent system's tier. Changing the tier needs operator. If the server refuses the change, the selector rolls back to the previous tier.

3.4Systems, pools and lifecycle#

Purpose
The list of adopted systems (things SolariNet monitors, with or without an agent): rename them, group them into pools, and see their lifecycle state.
Open
Sidebar → Systems, or select a pool card
Who
viewer to read; operator to rename, re-pool, create pools and change lifecycle; admin to purge

The table lists System, IP, Class, State, Targets (probe count), Pool and Heartbeat. The heartbeat bars are decorative, not a measurement. Decommissioned systems stay in the list, greyed. Deleted systems are hidden until you select the Deleted chip.

Create a pool and assign systems#

  1. Select New pool and type a name, for example DNS. Select OK.
  2. In each system's Pool column, choose the new pool from the drop-down menu. The change saves at once.

Rename a system#

Select the system's name (it has a small gear), type the new name and select OK. Renaming changes the display name only; the DNS name and SoR host name are separate.

System detail#

System detail opens when you select a system that has no agent, for example from Fleet Overview, Alerts or Topology. It shows Class, Pool and Heartbeat tiles, the criticality selector, lifecycle actions and the system's probe targets. Select a target to open Service detail. Remove on a target row stops that one probe, after a confirmation.

ActionEffectUndoRole
DecommissionProbing stops, open alerts are cleared, and the system stops counting toward the status panel. It stays in the list, greyed, with its history kept.Restoreoperator
DeleteAs Decommission, and the system also drops out of the lists. The record is kept so that, if the host turns up on a future scan, Discovery flags it rather than quietly adopting it again.Restoreoperator

Purge a deleted system#

  1. On Systems, select Deleted, then open the system.
  2. Select Purge. The dialog shows the stored name to type.
  3. Type that name exactly. The server checks it against the stored name.
  4. Select Purge permanently. A message confirms Purged name — row and probe history gone.

Every lifecycle action gives up after 15 seconds with no response after 15 s — try again, so a dialog never spins forever.

Service detail#

Service detail covers one probe target, such as tcp:nas:445. It shows the criticality inherited from the parent system, a Vantages table with each monitor's latest result, latency and loss, and Stop monitoring (operator), which removes the probe.

6.4How a change reaches the network#

The System of Record (MariaDB on cesium) is the single place where hosts, addresses, networks, DNS records and inventory are kept. Changing it from the dashboard starts an automatic chain. Three services on xenon run the chain.

StepWhat happensService
1You save a change, for example adopting a host or editing an address. The database records an event in the same transaction, so no change is lost.SoR on cesium
2The event is published on the message bus (RabbitMQ on benzene).sor-emit
3The DNS applier regenerates the zones from the current records, releases them on xenon, then refreshes each secondary server and checks that its serial matches. It also re-checks everything every hour.sor-apply-dns
4In the other direction, systems you adopt in Discovery are added to the SoR by address, and then flow forward to DNS like any other change.sor-reconcile

A new host should resolve within a minute or two of being adopted inferred. Check with the DNS page; if it does not, see Chapter 7.

7.9Questions#

Is anything I do here sent outside the house?
No. Barcode lookups check only Akoria's own catalog. Notifications go to the household's own phones and email.
Can I break something by looking?
No. Reading never changes anything. Changes need the operator role, and the dangerous ones (reimage, decommission, merge, purge) ask you to type a name to confirm.
What is the difference between retire, decommission and purge?
Retire stops monitoring and can be undone. Decommission also wipes SolariNet's data from the host and cannot be undone. Purge (admin only) permanently deletes the record of a system that has already been deleted.
Why does a viewer see buttons they cannot use?
Some screens do not hide controls by role. The server still refuses the action.
Where are licence keys kept?
Not in SolariNet. Inventory records only a reference to where a licence is kept.
Does the dashboard work offline?
It still opens, but shows only the sample fleet, and every change is blocked.
