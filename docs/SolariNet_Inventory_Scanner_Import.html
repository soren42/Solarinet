Inventory scanner import

SolariNet System of Record · Operator and developer guide · 22 October 2026

This guide covers the supported changeover from the standalone scanner-ingest app to the dashboard’s authenticated SoR inventory flow. The scanner remains the portable capture tool; the dashboard is the preferred write path into the shared inventory System of Record. A restricted local CLI maintenance path remains available.

Release state: The dashboard upload/import code, RackWire model-profile editor, and explicit physical-unit to SoR-entity association are implemented in the integration candidate. Tests cover JSX, PHP syntax, route authorization, UI behavior, scratch-MariaDB transactions, authenticated HTTP routes, and scanner-to-RackWire browser acceptance through cable commit. Apply is bound to the preview plan fingerprint and rejects a stale preview. The candidate is installed in an isolated, loopback-only Cesium development environment, where authenticated browser testing verified native network scan, live candidate recovery, and adoption into monitoring plus a SoR network entity. No scanner export has been applied to the live SoR; production dashboard deployment and production operator verification remain pending.

1. Operator procedure

  1. In scanner-ingest, open Export & backup and choose Download JSON under Migration data. Keep the downloaded file private as an inventory export.
  2. Open the live SolariNet dashboard and sign in with an operator account. Open Inventory → Scanner import.
  3. Select the downloaded JSON file. The dashboard accepts schema version 1 exports up to 4 MiB and shows the catalog item and asset counts before sending anything.
  4. Review location matching. A unique byte-for-byte name match can be used automatically. The preview lists every source location and its resolved SoR ID and name. For duplicates or renamed locations, select the intended SoR location by its visible ID and name. Case or accent differences require an explicit mapping. For an unmatched location, either stop and fix the mapping or explicitly choose to preserve its source text in notes with no SoR location assigned.
  5. Optionally match a scanner catalog item to an existing SoR model. Leave it unmatched to add or reuse the exact make/model. Optionally expand category mapping to override the automatic SoR hardware type for new models; categories that exactly match a type ignoring case map automatically, and unknown categories default to other. A category override does not change a model you matched to an existing SoR row. Review any assets marked repair; choose whether they should enter SoR as in_stock or retired. No repair default is selected.
  6. Choose Preview import. Check the insert/reuse/skip counts and warnings. Preview performs reads only and writes no inventory.
  7. Choose Apply import after checking the preview. Apply replans against the current SoR state and compares a plan fingerprint with the preview. If relevant inventory state changed, apply stops and asks you to preview again. A matching plan commits in one transaction or rolls back. On success, the dashboard refreshes its inventory view.
  8. To place an imported device in a connection plan, open Inventory → Components → RackWire device profiles. Select its SoR model, define connector groups, port counts, link speeds, PoE capability and budget, and device/port power values supported by the hardware, then save. Confirm the hardware specifications before using the profile for design decisions. Open RackWire and place the model; scan its barcode to resolve the unit from shared inventory.
  9. Before committing a cable to a network entity, open Inventory → Components and choose Link entity for the scanned unit. Search for and select the correct canonical SoR entity, then save. This explicit operator choice is recorded in the SoR audit log. A physical unit can link to only one entity, and an entity to only one physical unit. RackWire uses this link to resolve cable endpoints; it does not guess from a matching name, model, IP address, or device type. You can change or remove the link from the same component row.
  10. For port-level cable records, select the RackWire device and enter an explicit PORT MAP in its inspector. Map each existing SoR interface name to the matching RackWire port ID, such as GigabitEthernet0/3=ge-3. Check the device label and physical port before saving. The scanner import does not create network interfaces; if neither the port ID itself nor one unique mapping resolves to an existing SoR interface, RackWire keeps that cable endpoint at entity level.
Location identity matters. The SoR may contain more than one location with the same display name. Select by location ID after confirming the physical destination. Do not map a scanner label to a similarly named location by guesswork.

Realtime network discovery and host ingest

For network-attached systems, open Discovery in the dashboard, enter an intranet IPv4 range, and start a bounded scan (up to 4,096 addresses). The current integration candidate requires the entire range to fit inside RFC1918 private space, loopback, or IPv4 link-local space; public ranges and ranges that cross those boundaries are rejected by both the dashboard API and native worker. The loopback-only Cesium development instance runs dev-20261022-2cb099c-static, which includes this policy. Authenticated browser acceptance confirmed that 192.0.2.0/24 is rejected and a permitted 127.0.0.1/32 scan completes, saves one candidate, and displays it in Discovery. SolariNet queues the scan and returns immediately while the native worker probes hosts. The page polls job progress every second and refreshes saved candidates every 2.5 seconds while the worker runs, so reachable hosts can be reviewed before the scan finishes. Polls do not overlap; leaving Discovery cancels its active status request and returning resumes updates. Review each candidate, correct its name or class where needed, then choose Adopt to add it to monitoring. Adoption also mirrors the host name and IP address into the SoR network entity/address records, where normal SoR synchronization can publish supported network facts.

Keep the two ingest paths distinct. Network discovery identifies and monitors reachable hosts. Adoption creates or updates a SoR network entity, but does not create a physical hardware_units asset, barcode, purchase/location record, or verified RackWire model profile. Use scanner-ingest import or the inventory editor for physical equipment. For an adopted host that also has a physical asset, explicitly link the component to the entity in Inventory → Components before committing a cable. The authenticated browser flow verifies candidate refresh before scan completion using a controlled fixture. A separate native-worker acceptance scanned the local 10.0.0.0/24 directly, processed all 254 addresses, and recorded 14 candidates in a disposable database; the local listener appeared in Discovery while the scan was still running. Larger ranges and deployed worker behavior remain unverified.

2. Import behavior

Scanner dataSoR behaviorOperator consequence
Catalog itemReuses an existing exact make/model or inserts a hardware model. The scanner UUID is retained in external_refs; original item fields are preserved in notes.Use an explicit model match only when the destination model is the same product.
Physical assetInserts one hardware_units row with its tag, serial, mapped location, quantity 1, stock state, and scanner provenance.An existing asset tag/serial collision stops the entire transaction for reconciliation.
Asset tag and serialCreates per-unit barcodes records where values are present. Original scanner details remain in notes.A code already assigned elsewhere is a conflict; no code or unit is overwritten.
Archived source rowsArchived catalog items and assets are skipped. Active assets cannot refer to an archived item.Restore or correct source records in scanner-ingest before export if they should be active.
Repair statusRequires an explicit choice of in_stock or retired.Resolve physical condition before applying; SoR has no repair stock state.

Each imported fact is stamped with the scanner-ingest source and a dashboard operator audit entry. Repeating the same export is idempotent: unchanged rows are reused. If a previously imported row differs from its SoR state, the import stops and leaves existing data unchanged. Reconcile the discrepancy in the SoR or correct the source record before retrying.

3. Failure and recovery

Message or conditionAction
Wrong schema, malformed JSON, or file too largeExport JSON again from scanner-ingest. The importer accepts only schema version 1 and caps the upload at 4 MiB.
No unique SoR location / ambiguous locationChoose a destination by ID, or deliberately preserve the source label in notes. Verify the physical room or bin first.
Repair status needs a decisionInspect the asset and choose in_stock or retired before previewing again.
Existing inventory collision or changed prior importStop and reconcile the matching asset/model in the SoR. The importer is insert-only and does not repair existing rows.
SoR unavailable or transaction failedNo partial import is committed. Restore dashboard-to-SoR availability, then preview again.

The importer serializes concurrent applies with a MariaDB advisory lock shared with the standalone CLI. The lock is released after success or failure. The dashboard session, operator role, and CSRF policy protect both preview and apply routes. The standalone scanner app remains loopback-bound by default and does not need to be exposed to the LAN.

Preview returns a SHA-256 fingerprint over the normalized insert plan, counts, warnings, and resolved locations. Apply recomputes it after acquiring the shared import lock and refuses a mismatch. The database timestamp is excluded from the fingerprint because it is generated when rows are inserted.

4. Developer contract

  • dashboard/api/lib/ScannerImport.php validates the portable snapshot, inspects destination schema and enum constraints, builds bounded lookup indexes for the fields it matches, confirms candidates with SoR collation rules, and executes one insert-only plan transactionally. Preview and apply share the planner.
  • POST /api/inventory/scanner-import/preview and POST /api/inventory/scanner-import/apply are operator routes registered through the existing inventory policy. Payload: {snapshot, mapping, repairStatus, unmappedLocation}; apply also requires the preview's 64-character expectedFingerprint.
  • Supported mapping keys are locations (scanner label → SoR location ID), models (scanner item UUID → SoR model ID), and categories (scanner category → SoR hardware type). The UI exposes all three. Category matching defaults to a case-insensitive exact hardware-type name, then other; an explicit category choice only affects newly created models.
  • Snapshot bounds: at most 1,000 items and 5,000 assets; request body at most 4 MiB. The byte cap accommodates realistic exports at the full row limit while remaining below PHP's standard 8 MiB post body limit. Source IDs must be canonical lowercase UUIDs, matching scanner-ingest exports; uppercase variants are rejected because SoR external-reference keys use a case-insensitive collation. Archived state and version are validated before DB access.
  • Destination tables must use InnoDB and match the required columns from SoR migrations 014 and 015, including external_refs, barcodes, and audit_log. Length, enum, soft-delete, collation, reference, and uniqueness checks fail closed.
  • The scanner app’s JSON export is the interface. No direct browser call to its unauthenticated local API, remote DB credential, LAN listener, or server-side JavaScript is introduced.

Restricted local CLI maintenance path

scanner-ingest/export_sor.py remains available for a named operator on a controlled host when the dashboard path cannot be used. It connects directly to MariaDB and is not the default changeover path. Use a restricted database account, the verified SoR TLS CA, and an approved import window. The CLI preview is read-only; applying requires the explicit --apply flag and a single transaction. It does not grant access to the scanner's LAN service or copy its database credentials into the dashboard.

  • It reads SQLite in read-only/query-only mode and imports only active catalog items and assets. Archived rows are skipped; it does not infer SoR deletion or archive actions.
  • CLI preview returns a plan fingerprint; --apply requires that fingerprint and rejects a changed plan. The dashboard and CLI share the same MariaDB advisory lock.
  • Use an explicit mapping file for scanner locations, model IDs, or categories that do not match the SoR. Repair state needs an explicit --repair-status in_stock or --repair-status retired; unmatched locations stop unless --unmapped-location notes is deliberately selected.
  • UUID references make repeated unchanged imports idempotent. Existing inventory is never overwritten; changed source rows, barcode collisions, soft-deleted references, and destination length violations stop for reconciliation.
  • scanner-ingest/sor-importer-role.sql defines the CLI role: SELECT on sources, hardware_models, hardware_units, locations, external_refs, and barcodes; INSERT on those write tables plus audit_log. It grants no UPDATE, DELETE, DDL, or audit-log reads. Provision a dedicated account with a host restriction and protected secret outside Git; do not reuse the broad SoR synchronization account.
  • Live SoR preview on 21 October 2026 found an insert plan for two catalog items and two assets. Both source location names were deliberately retained only in notes because neither matched a live SoR location. Preview was read-only. The available synchronization account has broader privileges than the CLI needs, so no live apply or role provisioning has been performed.
  • The role definition and preview/apply/replay path passed all 15 database-backed exporter tests on disposable MariaDB 11.8.6, including denial checks for UPDATE and DELETE. The tests must never target production.

See scanner-ingest/EXPORT-SOR.md for the full command contract and field mapping. Keep the dashboard flow as the normal operator path after its release is deployed.

5. UI style decisions

The import is embedded in Inventory and follows the dashboard’s existing dark, compact administrative UI. The workflow has one primary action at each stage: select the file, review mappings, preview, then apply. Advanced model and category mapping are collapsed by default. The category section states the automatic mapping and fallback; location IDs stay visible where duplicate names need distinction. Errors are announced in an alert region, asynchronous results use status text, controls remain keyboard reachable, and no motion is required to understand the state.
