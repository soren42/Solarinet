Monitoring Overhaul

SolariNet Monitoring · why the graphs were blank, and a robust four-tier monitoring infrastructure · 2026-07-03

Headline. The dashboard's graphs "never showed data" for two unrelated reasons — one on the read path (fixed) and one because an entire monitoring tier was never producing rows (now producing). Host metrics were always being stored; the fleet sparklines just weren't served them, and the reachability tier had no reporting vantage. Both are resolved, plus network-throughput history and a portable remote-outpost tier now live on xenon + benzene.

Remote monitoring outposts

A monitor "outpost" is a portable prober that checks reachability from its vantage and reports to the server over mutual TLS. Multiple vantages give path-diverse reachability (a target down from one outpost but up from another localizes the fault).

# build a portable outpost bundle (monitor + matched TLS libnng) for an arch
deploy/build-outpost.sh x86_64        # or: arm64  (Pi Zero 2 W-class)

# deploy an outpost (local, or --host user@remote)
deploy/deploy-monitor.sh --name benzene-mon --host jason@benzene.akoria.net \
    --server tls+tcp://xenon:7701 --server-ip 10.0.0.20 --op admin
  • Enrollment: each outpost gets a cert with CN monitor.<name> — the server derives role from the CN and only a monitor may send MONITOR_REPORT (a client.* CN is rejected ERR_AUTH_ROLE). Signed via the bridge SIGN; the CA key never leaves the server.
  • Targets: pulled from the probeTarget table into monitor.conf (target = icmp:host / proto:host:port). ICMP works unprivileged on Linux.
  • Portability: the outpost carries its own TLS-enabled libnng.so.1 and LD_LIBRARY_PATHs it — some distros (openSUSE) ship an nng whose TLS transport is ABI-incompatible, which is exactly why benzene initially spooled instead of reporting. Built on a debian:bookworm glibc floor so the same binary runs on Pi OS / appliances.
  • Mesh (available, not yet enabled): the [peer] gossip + rendezvous-hash ownership lets N outposts split targets so they don't all probe everything — useful as the fleet of Pi outposts grows.

Verification

  • Fleet sparklines: /api/nodes returns 40-point cpu/ram/disk/net series per node.
  • Net history: netKbps writes per report (xenon ~1320 Kbps) and serves via /history?metric=netKbps.
  • Reachability: probeCurrent = 2 vantages × 18 targets; probeHistory accumulating; /api/probes returns per-target multi-vantage RTT/loss.
  • Server unit tests: 23/23. PHP lint + JSX transpile clean.

Follow-ups (scoped, not yet built)

These came out of the deep-dive and are the next increments toward "robust":
  • SNMP tier — enable SOLARI_WITH_SNMP, poll networkGear (ifHCIn/OutOctets, sysUpTime, status) into a partitioned gear-interface history table + dashboard charts.
  • Ingest timestamp from frame header — stamp hostHistory/probeHistory sampledAt from the frame's sendTimeUnixMs so store-and-forward spool replays land on the real sample time.
  • History self-maintenance — systemd timers for roll_history.sql (monthly partition creation) + retention.sql (nightly prune); surface retention as a server.conf knob.
  • Read-path downsampling — the /history endpoint truncates wide windows to the first N; bucket/downsample over the requested range instead. Give Sparkline an explicit empty/collecting state.
  • One-click target adoption — wire CTRL_ADOPT_TARGET so dashboard-added probe targets start producing series without redeploying outposts.
  • Pi-Zero outpost fleet — the arm64 bundle is built; deploy to the low-power Pis and enable the [peer] mesh so they split target ownership.
  • Infra self-monitoring — alert on ingest lag, stalled series, spool depth, partition health, vantage quorum, so a silent write-side failure surfaces instead of manifesting as blank graphs.
