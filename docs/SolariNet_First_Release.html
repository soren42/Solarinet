SolariNet — First Release

Fleet monitoring, provisioning & management for the homelab — the first fully-functional iteration · 2026-07-05

What shipped. Six pull requests took SolariNet from "graphs and screens" to a working operator console: agents now actually apply pushed config (convergence closes), discovered hosts are fingerprinted (OS/vendor/role/MAC), the dashboard surfaces issues instead of hiding them, operators can remove systems/apps and see who they are, and the deploy tooling is strictly standard C. All merged to main, CI green, dashboard live, server deployed.

Architecture (unchanged, reaffirmed)

A standard-C control plane (solariServer + agents over the SCP/TLS protocol) is the only writer of state; the PHP/JSX dashboard is a strict read layer, and every mutation is marshalled as a one-line VERB k=v request over the solariCtl AF_UNIX bridge, which holds the CA material, enforces operator RBAC, and re-emits control frames. The web tier never holds a server certificate and never writes the monitoring tables.

The four workstreams

1 · Config application, end to end #8

The headline gap: the server persisted per-node config and published directives, but no agent received or applied them, so appliedEpoch never advanced and every push showed permanent drift. Agents now SUB to the fleet PUB channel, apply the config blob (sample interval, watched processes, log patterns; monitors: round interval, probe set), persist it across restarts, and reply CONTROL_RESULT so convergence closes. Epoch-monotonic (a re-push acks-as-converged, never thrashes); directives are addressed (TLV_CTRL_TARGET_NODE) so the broadcast channel only acts where intended; a structurally-malformed addressee is rejected fail-closed. Fixed a latent nng bug (SUB sockets never subscribed) and a dashboard bug that misrouted node config pushes to the fleet-provision endpoint. 29-test IO build incl. a real PUB→SUB→CONTROL_RESULT loopback.

2 · Discovery & autoprovision enrichment #9

Discovered hosts used to show little more than an IP. They now carry an OS guess, vendor, device role, MAC, and SNMP sysDescr — from nmap -O -sV, snmpget, and avahi, best-effort and gated behind SOLARI_WITH_DISCOVERY_TOOLS so the core scan stays dependency-free. A bundled 54-entry OUI→vendor table covers common gear; a pure, unit-tested rule engine infers the role (printer/nas/camera/network/ap/gateway/iot/server/…), which pre-selects the adopt classification. Every host value is whitelist-sanitized before any shell-out.

3 · Issue surfacing + operator identity #11

A new Attention panel atop the fleet aggregates everything wrong — down/degraded systems, failing/split probes, crit+warn alerts, config drift, stale nodes, pending enrollments — into one ranked, deduplicated, click-through list (with a calm "all systems nominal" state). Problem-first ordering, clickable KPI filters, honest staleness, a crit+warn nav badge, per-alert acknowledge, and an SSE live feed round it out. Operators finally see who they are: a profile chip (name + role badge) with a Log out button, backed by the existing whoami/ logout endpoints.

4 · Removal, lifecycle & config depth #10 · #12

The catalog was append-only; now an operator can remove a monitored system (cascading to its targets and purging probe history), remove an individual service target, delete a pool (assets reassign to Unassigned), delete/create alert rules, retire a node, and acknowledge an alert — all through new RBAC-gated, audited solariCtl verbs (ASSET_REMOVE, TARGET_REMOVE, POOL_DEL, RULE_DEL, ALERT_ACK, and a dashboard-reachable RETIRE). The UI fronts every destructive action with a danger modal — typed-name confirmation for system removal and decommission (with per-scope wipe checkboxes). Retired nodes are filtered out of the roster by default; the discovery auto-discover toggle now persists.

Activation notes (ops)

  • Config-apply fleet rollout: the server side is live. To apply pushed config on a node, its agent must run the new binary (the SUB receive path) — roll out via deploy/remote-deploy.sh / deploy/deploy-monitor.sh. Until an agent is updated it keeps reporting exactly as before (no regression); it simply won't converge config.
  • Discovery enrichment is active on this server (built with -DSOLARI_WITH_DISCOVERY_TOOLS=ON; nmap/avahi/net-snmp present on xenon). The next scan enriches; existing rows show until re-observed. nmap -O OS detection needs raw-socket privilege; -sV works regardless.
  • Alert acknowledge sets clearedAt; the GET alerts payload has no separate "acknowledged" state, so an ack currently reads as cleared. A distinct ack state is a small follow-up if wanted.
UniFi netboot. The PXE/TFTP infrastructure is fully staged and verified (embedded iPXE loaders, TFTP-only service, all installer images), and the boot options are set in the UniFi config store. The last-mile force-provision is blocked by a controller SSO admin lockout; it completes with a one-click Save on Network → LAN → DHCP → Network Boot (or once the account unlocks). No LAN-disrupting workaround was applied.

Deferred (documented, not built)

  • LDAP/AD directory auth (fail-closed stub + config surface already in place), and a user-management CLI.
  • Login rate-limit / CSRF token (intranet-scoped; SameSite=Lax + bcrypt today).
  • A writable server-facet config API (server.conf stays file+restart, surfaced read-only).
  • Partition-maintenance timers for the history tables; a build-artifact publish path.
