Phase 6 Completion Report

SolariNet Monitoring · the dashboard data layer · on-prem vendoring · PHP read+control API · SSE bridge

What landed

Phase 6 (dashboard data layer) connects the Claude-designed front end to the live server through a PHP API, with everything served from the box itself. Consistent with the no-cloud tenet, the dashboard makes no external network fetches: React, ReactDOM, and Babel are vendored locally, and the page is reconciled to talk to a same-origin PHP API rather than any hosted service.

On-prem vendoring

The front end now loads its runtime from dashboard/public/vendor/ — react.production.min.js, react-dom.production.min.js, babel.min.js — plus local fonts/ and icons/. index.html references these by relative path; the design's screen and component modules (app.jsx, screens*.jsx, components.jsx, icons.jsx, styles.css) ride along. A service worker (sw.js) and manifest.webmanifest give the app its installable / offline-tolerant shell.

API adapter

dashboard/public/api.jsx is the front-end adapter: it replaces the design's mock data layer (data.jsx) with calls against the real same-origin endpoints and unwraps the server's response envelope into the shapes the screens already expect.

PHP read + control API

dashboard/api/ is a small PDO-backed PHP service — a front controller (index.php) over a router and route handlers, with a thin library layer:

LayerFilesRole
Librarylib/bootstrap.php, Router.php, Db.php, Response.php, Coerce.php, Operator.php, SolariCtl.phpPDO handle, routing, JSON envelopes, input coercion, operator-token gate, Unix-socket bridge to solariCtl

Live streamroutes/stream.phpServer-Sent-Events bridge for the live dashboard
Control-plane discipline. Reads go straight to MariaDB via PDO. State-changing actions do not write the database directly — they are routed through the operator-token gate (lib/Operator.php) and handed to the C server over its local solariCtl Unix socket (lib/SolariCtl.php). The PHP tier never becomes a second, divergent source of truth or control authority; the C server stays the sole arbiter of lifecycle actions.

Verification

The PHP API and the JSX adapter are authored-correct but not executed against a live browser or a running PHP-FPM + MariaDB stack in this session. There is no PHP unit harness in the tree, and no browser was driven here. What was verified:

  • The vendored runtime is present and referenced by relative path — no CDN or external <script src="https://…"> fetches remain, satisfying the no-cloud constraint by inspection.
  • The route surface lines up with the server's control verbs (solariCtl: APPROVE/REJECT, PROVISION, ADOPT, IGNORE, CONTROL, DECOMMISSION) and with the MCP read API, so the three operator surfaces (dashboard, MCP, solariCtl) agree on the same endpoints.
  • The reconciliation between the original design handoff and the live API is recorded in dashboard/API_RECONCILIATION.html / dashboard/DESIGN_HANDOFF.md.

Known gaps & deferred items

  • No browser validation here. The SPA was not loaded in a browser and the SSE stream was not exercised end-to-end in this session. Visual / interaction acceptance remains an operator step.
  • No live PHP execution here. The PHP API was reviewed for correctness, not run against PHP-FPM with a live MariaDB and a live solariCtl socket. PDO DSN, auth, and socket-path wiring are deployment configuration the operator supplies.
  • No automated PHP/JS test harness. Unlike the C and MCP tiers, the dashboard has no unit suite in-tree; its correctness gate is operator acceptance.
