SolariNet Status Panel

Developer reference · firmware, daemon, protocol, and dashboard integration · 21 October 2026

This guide is for engineers changing the Galactic Unicorn panel or its supporting software. The normative contracts remain status-panel/protocol.h, CONTRACT.md, CONTRACT-CP.md, CONTRACT-AW.md, and CONTRACT-SW.md; this reference explains how those pieces fit and how to verify a change.

Observed architecture: xenon composes fleet data and panel commands in the dashboard API. lithium runs solariPanel, which polls over verified HTTPS and transports snapshots/commands to the RP2350 over USB CDC. The firmware renders locally and reports state. An optional authenticated TLS listener supports the network transport path described by the software contract.

2. Wire protocol and compatibility

status-panel/protocol.h is normative and protocol.c is compiled by both daemon and firmware. The frame uses magic bytes A5 53, protocol version 01, type, little-endian payload length, payload, and CRC-16/CCITT over version through payload. Maximum payload is 2048 bytes; an incomplete frame expires after 500 ms. Parsers resynchronize on magic and reject bad CRCs without treating partial data as a message.

DirectionFramesPurpose
Host → panelSNAPSHOT 0x01, PING 0x02, HELLOREQ 0x03, CONTROL 0x04, PROVISION 0x05Fleet snapshot, link keepalive, capability/state request, idempotent control, USB-only provisioning chunks
Panel → hostHELLO 0x81, EVENT 0x82, LOG 0x83, STATE 0x84, CONFIG 0x85, PROVACK 0x86Firmware identity, local events, diagnostics, consumed command/device state, persisted preferences, provisioning progress
Compatibility rule: use the shared codec and fixed offsets; never cast a C struct onto wire bytes. Keep unknown frame types skippable, preserve additive payload handling, and make rollout order explicit in the relevant contract before changing a payload or command meaning.

CONTROL commands are re-served until a STATE frame reports lastCmdId. A successful serial write does not complete a command. The firmware consumes IDs in ascending order, including invalid commands it rejects; server-side validation should make rejection unreachable in normal operation. A firmware reboot may replay still-pending idempotent commands during the bounded queue window.

4. Daemon and API integration

The daemon implementation is standard C in status-panel/daemon/. It uses libcurl, OpenSSL, and the vendored cJSON 1.7.19 source. API TLS verification is enabled with the installed CA bundle; HTTP redirects are disabled; requests have bounded connect and total timeouts. The password is read from a dedicated file whose ownership and mode are checked. Keep secrets out of argv, logs, fixtures, and documentation.

  • Configuration example: daemon/solari-panel.conf.example. The default serial glob is /dev/serial/by-id/*; a literal device path is also accepted.
  • Systemd unit: daemon/solari-panel.service. It runs as jason, uses the dialout group, restarts after failure, and applies filesystem/kernel restrictions.
  • Snapshot cadence defaults to two seconds; API polling defaults to five seconds. Transient API and serial failures preserve last valid data and use retry/backoff paths.
  • Optional listener configuration requires an explicit bind address, TLS server certificate/key, client CA and allowed SAN. Wildcard binds are rejected by the daemon.
  • The API service principal is read-only for fleet data and has narrowly scoped state/config reporting. Dashboard operators control command creation; UI role checks are not the authorization boundary.
Never claim a hardware rollout from host tests. Deployment acceptance also requires firmware identity/build checks, physical controls, alarm behavior, disconnect/reconnect, API outage recovery, and the applicable cross-lab review.

5. Build and test workflow

Portable daemon

cd status-panel/daemon
make clean
make
make test

Build flags include C99, -Wall -Wextra -Werror. The listener test creates temporary certificates and exercises valid and invalid client identities, CA, certificate purpose, expiration, denylist, and file permissions.

Firmware state machines and rendering

cd status-panel/firmware/test
make clean
make

This uses the host compiler only; it does not build a flashable UF2. It covers link ordering/liveness, commands, configuration, provisioning, help, network state, power, renderer safety, and framebuffer parity fixtures with sanitizers on selected suites.

Hardware firmware build

cmake -S status-panel/firmware -B /tmp/solari-panel-build \
  -DPICO_SDK_PATH="$HOME/pico/pico-sdk" \
  -DPIMORONI_PICO_PATH="$HOME/pico/pimoroni-pico" \
  -DCMAKE_BUILD_TYPE=Release
cmake --build /tmp/solari-panel-build -j4

Expected artifact: solari-panel-fw.uf2. The target is Pico 2 W/RP2350. A host test pass is not a substitute for the Pico toolchain build or device verification. Flashing is an operator action and needs its own explicit authorization and evidence.

6. Change checklist

  1. Read the owning contract and inspect the current implementation before editing; contracts outrank this summary.
  2. For wire changes, update the normative header/codec and both consumers together. Add fixtures that cover old/unknown/malformed cases and sequence behavior.
  3. For UI or render changes, update the design reference, firmware renderer, virtual dashboard view, and parity fixtures as applicable.
  4. Run the focused host tests, daemon tests, relevant dashboard/API tests, and firmware build for the touched boundary. Record commands and outcomes.
  5. Update user/developer manuals and paired PDFs when behavior or operating procedure changes. Keep dated status claims distinct from verified current state.
  6. Obtain independent cross-lab review for security, protocol, migration, or live rollout changes. Exercise rollback before live changes; do not infer deployment success from candidate tests.
