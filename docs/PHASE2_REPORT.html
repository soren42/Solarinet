The core + spool suites are the hard gate; the nng TLS loopback round-trips a frame end-to-end. The staged bootstrap-xenon.sh run reports them separately so a transient transport wrinkle can't mask core success.

One test was strengthened, not just flipped on. The config suite previously only asserted the dependency-free stub (solariConfigOverlayJson → ERR_PLATFORM). With SOLARI_WITH_JSON now compiled in, that assertion would have been wrong, so the test branches on the (now PUBLIC) SOLARI_WITH_JSON macro and verifies the applied-overlay path for real: string/number/bool entries merge, malformed JSON and NULL are rejected cleanly. The base dependency-free build keeps asserting the ERR_PLATFORM stub.

Dependencies

nng (v1.8.0), mbedTLS (3.6.x), SQLite (3.46+), and cJSON (1.7.19) are resolved from the host's dev packages, installed/idempotently checked by deploy/bootstrap-xenon.sh; the CMake links either vendored-source targets or the system libraries, whichever is present. Using system packages here (rather than strict vendoring) is the deliberate, pragmatic stance — self-host what matters, don't chase hard air-gapping.

Build it yourself

./deploy/bootstrap-xenon.sh           # installs deps, builds, runs the staged suites
# or directly:
cmake -S . -B build -DSOLARI_BUILD_TESTS=ON \
      -DSOLARI_WITH_IO=ON -DSOLARI_WITH_SQLITE=ON -DSOLARI_WITH_JSON=ON
cmake --build build && ctest --test-dir build --output-on-failure
