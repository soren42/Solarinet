Inventory API Reference

HTTP contract for reading and editing the inventory System of Record through the authenticated SolariNet dashboard API. This guide covers list pagination, filters, catalog writes, response metadata, and compatibility behavior.

Revision 1.4 · 2026-11-03 · Location move, merge, and container API added · Internal

1. Authentication and transport

Use the dashboard’s normal same-origin HTTPS session and its configured API base. Reads require an authenticated dashboard session under the deployed authorization policy. A successful response uses the common envelope {"ok":true,"data":…,"ts":"…"}; failures use {"ok":false,"error":{"code":"…","message":"…"}}. Do not send database credentials to a browser client.

Add limit and/or offset to request a page. The page size must be 1–5000 (1–500 for /api/inventory/product-types); the offset must be 0–2147483647. If only one parameter is supplied, the other defaults to limit=500 or offset=0. Results have a deterministic order within each list.

GET /api/inventory/models?hw_type=server&limit=100&offset=200

A paginated response places rows in data.items and returns:

{
  "ok": true,
  "data": {
    "items": [{"id": 123, "make": "Example", "model": "Unit"}],
    "page": {
      "limit": 100,
      "offset": 200,
      "total": 237,
      "hasMore": false,
      "nextOffset": null
    }
  },
  "ts": "2026-10-21T00:00:00Z"
}

Continue while page.hasMore is true, using page.nextOffset. The total is the number of rows matching the same filters, before pagination. Inserts or deletes between requests can shift offset pages; clients that need a consistent export should use a stable snapshot workflow rather than assuming offset pages form a transaction.

3. Compatibility behavior

Important: Omitting both pagination parameters preserves the pre-existing response shape: data is an array. Components retain their existing default limit of 500; the other list routes remain unbounded in this compatibility mode.

The combined GET /api/inventory endpoint retains its existing object shape—models, units, locations, receipts, projects, and allocations—for inventories with at most 500 rows in each collection. It executes bounded queries and returns HTTP 413 with inventory_page_required if any collection exceeds that threshold. It does not accept page parameters. Integrations that need larger inventories should call the individual paginated list paths above.

The dashboard browser adapter now requests those collection paths at 1000 rows per page, validates page totals and boundaries, and assembles the complete inventory snapshot for existing cross-reference workflows. The Components table filters and sorts the full loaded collection but renders 100 rows per page; Receipts and Projects also render at most 100 entries per page. The location hierarchy opens top-level children and lets operators expand deeper branches on demand. The adapter keeps a five-second in-memory snapshot to avoid repeating the fan-out during bootstrap and screen mount. A collection larger than 100,000 rows, or a changed total/duplicate page boundary during the read, is surfaced as an inventory load error rather than silently truncated. Same-count field updates do not have transaction snapshot isolation; reload for a fresh view.

Migration advice: Request ?limit=500&offset=0 explicitly, then consume items and page metadata. This makes the bounded response shape explicit and leaves legacy array consumers unchanged.

All list filters and pagination values are handled by the server. Do not interpolate user-provided values into SQL or treat a returned row as authorization to mutate it; write operations have separate authorization and CSRF checks.

5. Product catalog

Product types describe reusable products; each physical or software instance remains a separate hardware_units item. Product types and barcode writes require an operator or admin session, same-origin request provenance, and the session-bound X-Solari-CSRF token. Reads require a session.

Method and pathBehavior
GET /api/inventory/product-types?q=&kind=&limit=&offset=Search live types by name, brand, model, or category; optional kind filter; paged response.
GET /api/inventory/product-types/{id}Read one live product type.
POST /api/inventory/product-typesCreate a product type. Optional barcode object attaches a code in the same transaction.
PUT /api/inventory/product-types/{id}Partial update of kind, name, brand, model, category, specs, notes, or image URL. Optional updated_at detects stale edits.
DELETE /api/inventory/product-types/{id}Soft-delete a type; existing references remain and deleted types leave pick lists.
GET /api/inventory/product-barcodes?code=Exact normalized lookup only. It returns a prefill candidate and never creates a type or item or calls an external service.
POST /api/inventory/product-barcodesAttach product_type_id, code, and optional code_type (gtin, sku, or other).
DELETE /api/inventory/product-barcodes/{id}Soft-delete a code.

Names are required and trimmed. Product type kinds are hardware, peripheral, component, software, accessory, consumable, and other. Secret-like keys such as password, token, credential, or licence key are rejected recursively inside specs; licence data must be a non-secret reference. Barcode codes are upper-cased with whitespace removed and unique while live. Declared GTIN codes must have a supported length and valid check digit. Validation uses bad_request (400), missing rows use not_found (404), duplicate codes use duplicate_barcode (409), and optimistic update conflicts use conflict (409).

6. Location schema

Locations use the levels property, floor, room, section, and storage_unit. A root must be a property. Ordinary parent transitions are property → floor → room → section. Storage units may be placed under any level and may contain other storage units. The database enforces these transitions and rejects parent cycles.

Live sibling names are unique, including among roots; soft-deleted rows release their name. Optional container_type_id references the editable, soft-delete container type catalog. Optional assigned_project_id records explicit container ownership and becomes NULL if its project is hard-deleted. Legacy site/building rows map to properties, rack/shelf/position/zone/cabinet/drawer/tray/bin/container rows map to storage units.

Location hierarchy and containers

Location writes require operator/admin authentication and the standard same-origin CSRF token. POST /api/inventory/locations accepts parent_id, required name and loc_type, optional code/notes, and optional container_type_id/assigned_project_id. Location rows now expose containerTypeId and assignedProjectId in the existing tree and flat response shapes. PUT /api/inventory/locations/{id} accepts the same metadata fields except parent (a parent_id key is rejected with bad_request; use /move); it requires the row’s updated_at (raw or ISO updatedAt) to reject stale edits.

Method and pathBehavior
POST /api/inventory/locations/{id}/moveSet parent_id (nullable). Checks cycles, level transitions and sibling names under transaction locks; records old and new parents.
GET /api/inventory/locations/{id}/merge-preview?target_id=…Returns source/target, reference counts by hard-FK and polymorphic history class, and a SHA-256 fingerprint.
POST /api/inventory/locations/{id}/mergeBody: target_id and preview fingerprint. Rechecks under lock, rewrites supported hard FKs and live location barcodes, preserves scan/external-reference history, then soft-deletes the source. Repeating the completed merge returns its deterministic result.
POST /api/inventory/locations/bulk-storage-unitsBody: nullable parent_id, count (1–500), and either a names array or prefix/start; optional code_prefix/code_start, container_type_id, and project_id. The full batch is validated and inserted atomically.
PUT /api/inventory/locations/{id}/projectBody: nullable project_id. Requires a storage unit. Clearing assignment is allowed only when no live child location or hardware unit remains; the location identity and code remain.
GET /api/inventory/container-types?include_deleted=1List live types by default; include retired rows when requested.
POST /api/inventory/container-typesCreate a named container type.
PUT /api/inventory/container-types/{id}Rename with required updated_at for optimistic concurrency.
DELETE /api/inventory/container-types/{id}Soft-retire a type. In-use types may be renamed or retired; locations are never auto-deleted.

Location errors use bad_request (400), not_found (404), duplicate_location, location_cycle, merge_conflict, container_not_empty, or stale-update conflict (all 409). A merge preview fingerprint expires when referenced rows or either endpoint changes.

7. Verification scope

The candidate’s HTTP integration test exercises list limits, page metadata, non-overlapping page boundaries, flat location pages, empty allocation pages, invalid zero limits, and the legacy aggregate’s 413 boundary against a disposable MariaDB instance. The browser adapter test traverses a two-page collection, checks stale-data behavior, and rejects over-limit and changing-total fixtures. Changed totals or duplicate IDs across pages fail the load and require a retry; page requests are not a database transaction, so same-count field updates may not be detected.
