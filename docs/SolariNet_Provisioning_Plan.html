A single pipeline from bare metal to a continuously-patched host — provision, enroll, configure by function, maintain on latest-stable, and retire cleanly — built as increments on the machinery SolariNet already has, not a rewrite.

What changed in Rev 2

This revision incorporates a prior design review (GPT-5.5, checked against the repository). It corrects three overstated claims, resolves five blockers into concrete design — host static-IP cutover, a single enrollment protocol with real endpoints, atomic IP allocation, the true xenon→benzene execution topology, and a de-circularised roadmap — and adds lifecycle edges omitted from the first draft. 01 Overview & architectural stance

What we are building, and the one decision that shapes everything downstream.

SolariNet can already stage a PXE install, mint an enrollment certificate, mirror hosts into a system-of-record, and push the agent to a running box. What it cannot do is run any of that as one motion, decide where a host belongs from its function, or keep the fleet current over time. This plan closes those gaps and unifies the pieces into a lifecycle — provision, configure, maintain, and retire.

Load-bearing decision

The dashboard orchestrates and observes; benzene executes. The PHP UI never SSHes into a host, never runs a playbook, and holds no CA key. It enqueues intent and reads back state. Concretely: the dashboard calls a solariCtl verb on xenon (where solariServer and the bridge actually run), which writes an immutable run record into the SoR and signals the message bus. A run-queue daemon on benzene consumes that record and drives Ansible. This is the same transactional-outbox pattern the sorsync daemons already use — and it means a compromised dashboard can enqueue a request but cannot itself touch a host or sign a cert.

Three principles follow and hold throughout:

  • The SoR is the single source of truth — and therefore is the Ansible inventory. Function tags live in the CMDB and drive inventory groups, IP allocation, package bundles, and config. There is no second inventory to keep in sync.
  • Function, not hostname, is the unit of intent. You tag a host database or auth; the system derives its subnet, package set, DNS name, and config from that tag.
  • Every layer is an increment. Each phase wires together something that already half-exists. We have two disconnected provisioning flows today; the first job is to make them one, not to add a third.
Scope boundary set in Rev 2

The covered footprint is glibc Linux servers (Debian / Ubuntu / openSUSE × x86_64 / arm64 / arm32) on IPv4. Musl/mips appliances wait on the static-musl build matrix (a pre-existing blocker); IPv6 allocation waits on address-family-aware DNS rendering. Both are named follow-ons, not hidden assumptions.

The core disconnect

Netboot's firstboot enrollment hook is a stub; Ansible's solarinet-client role uses a different mechanism (a pre-staged, control-node-held private key). There is no path today from "bare metal boots" → "enrolled in the SoR" → "Ansible converges." Building that single spine is Phase 1.

05 Function taxonomy — the semantic spine

The one new concept that makes "tag a host and everything follows" possible.

Today entities.role is a free-text sentence. We introduce a closed set of function tags. A host may carry several; each binds which network it belongs on, what software it runs, how it is configured, and its default criticality.

Illustrative rows — the exact set is a Phase-0 deliverable. Bundles reuse the existing common-stack "one logical list + per-OS name map" pattern, extended so each tag contributes its bundle atop the shared core.

Multi-tag precedence — decided up front

A host may carry several tags, so the taxonomy defines exactly one rule for conflicts: a primary_function per host selects the home network (never ambiguous), while package bundles union and config profiles apply in a declared tag order. Tag pairs that must never coexist (e.g. security + database on one box) are declared incompatible and rejected at tag time, not discovered at converge time.

06 IP allocation by function

The first logic to ever allocate from the network hierarchy — which means it must first be able to trust that hierarchy.

Prerequisite (G7) — resolved from a Rev-1 error

Rev 1 assumed subnets and dhcp_ranges were "seeded from UniFi." They are not — nothing populates dhcp_ranges, and subnets are synthesized /24s. The allocator must not run against inferred ranges with no pool boundaries. So a tested UniFi network import (VLANs, subnets, gateways, DHCP pools → SoR, with provenance + freshness) is a hard prerequisite, landed in Phase 0.

Given a trustworthy hierarchy, the allocator turns a function tag into a concrete static address — and does so atomically, because the schema does not enforce live uniqueness on its own (UNIQUE(address, deleted_at) permits many NULL rows; seed.py says as much):

allocateAddress(primaryTag, hostName): # IPv4 only in this phase subnet = subnetForNetwork(networkFor(primaryTag)) # taxonomy → one network → its subnet reserved = { network_addr, broadcast_addr, subnet.gateway_ip } BEGIN TRANSACTION # serialize concurrent allocators lock the subnet's allocation row (SELECT … FOR UPDATE) used = active addresses in subnet (via the enforced live-address key) pools = dhcp_ranges WHERE subnet_id = subnet.id # dynamic_pool + excluded spans cand = first usable host address in subnet.cidr NOT IN used AND NOT IN reserved AND NOT inside any dynamic_pool / excluded range INSERT entities(...); INSERT ip_addresses(cand, is_primary, assignment='static', …) COMMIT # unique index rejects any racing dup return cand

Two correctness requirements the review surfaced, both adopted:

  • Enforceable live uniqueness — add a generated active-address column (address where not-deleted, else NULL is disallowed) with a real UNIQUE index, so the database itself rejects a double-allocation even under a race. The transaction lock makes the common path clean; the index is the backstop.
  • Reserved-address rules — never hand out the network, broadcast, or gateway address, never anything inside a DHCP dynamic_pool/excluded span, and respect static_block semantics. A wrong role→subnet map is caught by validating the map and showing every first-run allocation for confirmation before commit.

Writing the entity + is_primary IP is enough for DNS (§7): CDC fires, sor_emitd publishes, sor_apply_dnsd renders A + PTR. Writes follow the existing Sor::upsertHost() pattern under a new provisioner row in sources for provenance. IPv6 allocation is deferred until DNS rendering is address-family-aware.

07 DNS & DHCP integration

One side is nearly free — within limits. The other is a real decision with a guardrail.

DNS — automatic, IPv4-shaped OBSERVED

A live entities row + a live is_primary IP is sufficient: v_dns_hosts selects it, CDC emits, sor_apply_dnsd renders A + PTR and reloads BIND only on change. Caveat: gen-zones.py emits only A and splits on dots for /24 in-addr.arpa — it is IPv4-only. A malformed or IPv6 row would break rendering, so allocation is IPv4-constrained and a pre-deploy zone validation gate is added.

DHCP — a genuine gap NEW

Appliers exist for DNS, AD, Pi-hole — none for UniFi/DHCP. dhcp_ranges is (once imported, G7) a mirror of the controller. Writing assignment='dhcp_reservation' records intent that currently goes nowhere.

The DHCP fork — with a lease guardrail

Provisioned hosts get a static address, so they don't strictly need a reservation to resolve. But the review flagged a real hazard: hosts install over DHCP, and sor_reconcile_discovery.py can mint a new entity for an adopted address not already owned — so a stale lease or a decommissioned host can create ghost identities or collide with controller state.

08 The lifecycle subsystems

What each part builds and reuses — now including the edges the first draft skipped.

8.1 · Provision — bare metal to enrolled, with the host actually on its IP

Extend the working PXE staging into a live, one-motion flow. The blocker the review caught: allocating an IP in the SoR does nothing if the host keeps its DHCP lease. So provisioning includes a host network cutover — an idempotent, per-distro step (preseed/late-command, cloud-init, AutoYaST script) that: selects the right interface by MAC, writes the allocated static IP + gateway + DNS resolvers, confirms connectivity, and falls back to DHCP on failure rather than stranding the box. Only after the host answers on its allocated address is the allocation committed as authoritative. Going live still requires the deliberate DHCP/PXE switch on benzene or UniFi — a conscious operator action, never a side effect.

8.2 · Enroll — one protocol, real endpoints

Today two mechanisms contradict each other: fleet-lib.sh::sign_node_cert() generates the private key on xenon and stages it over HTTP, while solari-enroll.sh expects the host to generate its own CSR + token — and there is no POST submission endpoint (provisioning.php is GET-only; enrollments_mut.php only approves/rejects). Rev 2 picks one protocol and specifies it:

  • Host-generated key, always. The private key is born on the target and never leaves it. Server-side key generation is removed.
  • New endpoints: POST /api/enrollments (submit CSR + enrollment token → pending), GET /api/enrollments/{id} (poll status), and the existing approve/reject transitioning pending → signed. A real enrollment_tokens table (bound to a pending host + its function tags, single-use, expiring) replaces the client-side fake "issue token" button.
  • One state machine: token-issued → csr-submitted → approved → cert-delivered → enrolled, each transition an auditable row.

8.3 · Configure — baseline + role bundles (after a trust refactor)

Generate a dynamic Ansible inventory from the SoR: tags → groups, entity row → host_vars. The existing roles are the foundation, but "apply as-is" was overstated — two things must be refactored first: the solarinet-client role copies a control-node-held private key (incompatible with §8.2's host-key rule), and ansible.cfg disables SSH host-key checking (a first-converge MITM exposure). Rev 2 refactors enrollment out of the role and pins host keys (from the enrollment cert / a known-hosts seed) before declaring reuse. New per-tag role bundles then layer the function's packages + config on the shared common-stack. shared-home and directory-join become baseline toggles.

8.4 · Maintain — the LSV lifecycle, made reproducible

The largest new capability, and the one the review pressed hardest on. Six parts:

  • Reproducible "latest stable." "Latest" is defined per distro by an immutable manifest promoted from a repository snapshot — the same manifest flows through every ring, so ring 3 can't silently get different packages than the canary. Not a live apt upgrade whose result depends on when it ran.
  • Version tracking — installed vs. manifest, per host, per component (OS set, role bundles, solariClient/solariMonitor). The control side /api/builds never had.
  • Health-gated rings — canary → ring 1 → ring 2 → critical. A ring advances only when its hosts pass tag-specific pre/post health probes (a database answers queries, not merely "package installed"), with quorum for clustered services.
  • Offline & deadline policy — each run snapshots its eligible population; unreachable hosts get a timeout + waiver + catch-up rule so one dark host neither stalls the ring forever nor is silently skipped and left unpatched.
  • Dry-run & diff — Ansible check mode reports likely deltas first, with the honest caveat that check mode can't fully predict scriptlets/restarts/migrations; irreversible steps (schema, data) are gated behind an explicit backup/snapshot.
  • Rollback / roll-forward — where the package manager supports history (zypper, dnf), roll back; where it does not (Debian), the manifest defines a tested roll-forward and a workload snapshot taken before the run. Reboot requirements are modeled, not assumed away.
Policy guardrail

LSV is the default, never a mandate: per-tag pins/holds, a global freeze switch, rings that contain a bad manifest to one canary, and mandatory dry-run. A database can deliberately lag the OS train.

8.5 · Observe — orchestrate & watch

The dashboard renders convergence, drift, ring/health status, and run history, and offers enqueue actions. It writes a run row and reads results; it never executes (§11).

8.6 · Retire — the terminal workflow NEW

Omitted in Rev 1 despite solariCtl.c already exposing DECOMMISSION/RETIRE. A retired host must not linger with a valid cert, an owned IP, DNS aliases, secrets, or update eligibility — and must not be resurrected by the discovery reconciler. The flow: quarantine → revoke cert → remove secrets → release IP + DNS/DHCP → drop from inventory/rings → write a discovery tombstone so sor_reconcile_discovery.py won't re-adopt the address → record wipe evidence. This reuses the existing tombstone lifecycle rather than inventing one.

8.7 · Re-tag — changing a host's function NEW

Tags drive network, packages, DNS, and config, so changing database → web is a migration, not an edit. The workflow: preflight (is the target tag compatible? does it force an IP/VLAN move?) → drain (stop/relocate services) → network cutover + DNS change if the home network changes → converge the new bundle → remove the old bundle's packages/secrets (no stale privileged software) → rollback on failure. Incompatible tag combinations are rejected at tag time (§5).

11 Execution engine

How intent becomes an Ansible run — with the real topology and crash/concurrency safety.

  1. Enqueue on xenon. The dashboard calls a solariCtl verb (PROVISION_RUN, CONVERGE, UPDATE_RING, RETIRE) — which runs inside solariServer on xenon, not on benzene. It writes an immutable runs row (params + a captured inventory-snapshot id) and signals the bus. No SSH, no CA key, no shell in PHP.
  2. Consume on benzene. A run-queue daemon on benzene atomically claims a run (lease + heartbeat), takes a per-host mutex so two runs can't mutate one host, regenerates the inventory from the snapshot id (so a mid-flight tag change can't alter a running job), and invokes ansible-playbook with the right --limit and tags.
  3. Stream + record. Output streams to a per-run log the dashboard already tails; on completion the daemon writes status + diff to run_attempts/run_targets; ring gates advance from health checks, not mere exit codes.
  4. Recover. A dead daemon's lease expires; the run is resumable or explicitly failed — never silently orphaned or blindly re-run.
Why not just copy the sorsync pattern

The sorsync appliers are idempotent renderers — re-running re-emits current state harmlessly. An Ansible/package run is long-lived and partially destructive; re-running blindly can double-apply or corrupt. So the runner is a workflow state machine with resumability and per-target reconciliation, not another renderer. It borrows sorsync's transactional-outbox enqueue, not its at-least-once re-execution.

Why not AWX / Semaphore

A full Ansible controller is more service to run, secure, and patch — on the ops hub. The run-queue abstraction is the seam to swap AWX behind later if scale ever demands it; it doesn't demand it now.

12 Security & supply chain

A fleet-wide "install and patch everything" system is a high-value target. The review sharpened where the real risk sits.

No execution surface in PHP

The dashboard enqueues and reads; execution lives on benzene. A compromised dashboard cannot SSH the fleet or sign a cert.

The real top risk: benzene + supply chain

benzene holds fleet SSH + update authority, and base-os grants fleet-wide NOPASSWD:ALL. Its compromise, or a poisoned artifact, is fleet root — a bad update can pass a naïve canary. Mitigations below are therefore mandatory, not optional.

Signed, immutable artifacts

Binaries and manifests are checksum+signature verified before use — including the firstboot fetch, which currently pulls over HTTP unverified. No unauthenticated mutable artifact enters the pipeline.

Segmented runner credentials

Not one omnipotent key: scope runner credentials by host group / ring, pin SSH host identities (no host_key_checking=False), and restrict which playbooks/vars a run may invoke.

Secret custody

Secrets via a vault identity with rotation — never --extra-vars on a command line (leaks via process inspection), never in group_vars, git, or a run log. Logs are redacted; no_log on sensitive tasks.

Certs, provenance, tombstones

Host-generated CSR → internal CA; the provisioner is a registered sources row; retirement revokes the cert and tombstones the host so it can't be silently re-adopted (§8.6).

15 Verification & observability

A fleet-mutating system whose defects first appear in production is a system without a test strategy. This is a phase gate, not an afterthought.

Allocator correctness

Property + concurrency tests: no reserved/gateway/broadcast address ever issued; no two live rows share an address under parallel allocation; pool boundaries honored. Runs in CI against a scratch SoR.

Disposable-VM acceptance

The provision→enroll→cutover→converge flow exercised end-to-end on throwaway VMs across the Debian/Ubuntu/openSUSE matrix, per phase gate — not first tried on a real host.

Failure injection

Forced-bad manifest halts at canary; killed runner daemon recovers via lease expiry; offline host is waived; mid-run tag change doesn't alter the running job. Each is a test, not a hope.

Runner observability

Daemon metrics: queue depth, run duration, stuck-run alerts, lease/heartbeat health, bounded+rotated logs, disk retention. The runner watches itself.

Every phase's acceptance criteria (§13) are backed by one of these; "green" means the suite passed, not that a command exited zero.
