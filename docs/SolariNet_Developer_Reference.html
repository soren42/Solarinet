About this document

Document control

This reference describes SolariNet — a self-hosted network monitoring, discovery, and control fabric written in standard C with a PHP dashboard — as it is actually built on the akoria homelab, alongside the architecture it is planned to become under the current stabilization program.

How this was assembled

The contents were reconstructed from ground truth, not memory: the committed source tree on branch stabilize/phase-0-containment; the rendered configuration live on the primary host xenon; the DNS source-of-truth netdb/akoria-hosts.yml; and an authorized live discovery pass across the homelab (host-liveness sweep plus read-only SSH fact-gathering). Network discovery on this infrastructure is routine, authorized administration of the operator's own network.

Reading the provenance flags

Every non-trivial claim is marked so a reader can tell measured fact from reasoning:

OBSERVED
Read directly from source code, live host state, or a discovery scan during assembly.
INFERRED
Deduced from surrounding evidence; not directly confirmed. Treat as a lead, not a guarantee.

Capability maturity is shown with the same labels the dashboard uses (planned track I0):

Prototype  Lab  Production  Authoritative

A feature marked Lab works but is not trusted for unattended production use; several such capabilities are explicitly frozen (see §10).

Scope & honesty note

SolariNet is under a declared feature freeze. Its own architecture review found that feature breadth had outrun enforcement and durability. This document therefore separates what is implemented and load-bearing from what exists in code but is not yet trustworthy — the distinction is the point, not a footnote.

Conventions

  • Hostnames, IP/MAC addresses, ports, node IDs, file paths, verbs, and code are set in IBM Plex Mono — the data face.
  • Hosts are named for periodic-table elements and compounds (an RFC 2100 convention); the name carries no functional meaning. Function is expressed as a DNS CNAME.
  • The control-plane binaries are solariClient, solariMonitor, solariServer; the wire protocol is SCP (SolariNet Control Protocol).

SECTION 01System overview

SolariNet is a self-hosted fabric that watches a homelab and acts on it: edge agents report host health, a monitor tier probes reachability, and a central server persists state, raises alerts, drives discovery, and brokers operator commands — all in standard C, fronted by a build-step-free PHP dashboard.

What it is

The system is a clean three-tier control plane — solariClient (per-host agent), solariMonitor (on-the-wire prober), and solariServer (ingest, storage, alerting, control) — speaking a single custom binary protocol, SCP, over mutually-authenticated TLS. Around that core sit a MariaDB datastore, a RabbitMQ notification bus, a DNS/AD System of Record with change-data-capture, and an identity stack (Keycloak federated to Samba Active Directory). The operator sees all of it through one dashboard served by Apache and PHP-FPM.

The codebase holds to two hard house rules that shape every decision below: the application is standard C with associated Makefiles, and the dashboard is PHP with no build step — React and Babel are vendored and JSX is transpiled in the browser at load. There is no Node.js in the runtime, no bundler, and no server-side JavaScript anywhere. OBSERVED (no package.json, composer.json, or lockfile exists in the tree).

The honest caveat: a fleet-of-one in practice

Read this before trusting the topology

The architecture is a genuine three-tier split, and the monitor tier's rendezvous-hash ownership is implemented in code. In production, however, nearly every node runs the client role only; the monitor tier and its k-of-n redundancy are not yet load-bearing. Treat multi-monitor resilience as designed-and-coded, not proven. Section 11 tracks the work (F-19/F-20) that is meant to make the claim true.

SECTION 02Control-plane architecture

Three C programs, one shared static library, and one binary protocol. Everything the fabric knows flows through solariServer; everything an operator does to it flows through a single local socket into the same process.

2.1   Three-tier topology & SCP transport

All three daemons link one static library, libsolari (lib/solari/), which owns framing, TLV, crypto, config, JSON, logging, time, the SQLite spool, and the nng transport. The core is zero-dependency; the transport (solariNet.c), spool (solariSpool.c), and reporter (solariReporter.c) compile only when their feature flags (SOLARI_WITH_IO, SOLARI_WITH_SQLITE) are set.

solariClient
Per-host agent. Collects host metrics, log tails, and process info behind a platform-abstraction layer (only platLinux.c exists today); reports over SCP; spools to SQLite when offline. Discovery advertises via mDNS/avahi.
solariMonitor
On-the-wire prober (probeNet.c: ICMP via unprivileged SOCK_DGRAM with fallback, TCP-connect, UDP, app-level). Targets are split across the monitor fleet by rendezvous (HRW) hashing at a replication factor — no coordinator. Linux-only.
solariServer
The hub: validates and dispatches frames, persists to MariaDB, runs the alert engine, discovery enrichment, SNMP polling, provisioning, the leadership lease, and hosts the solariCtl operator bridge. Also builds solariSnmpPoll and solariCtlClient from the same core.

SCP frame & ingest gate

Every frame is validated by solariFrameParse (magic, version, CRC) before dispatch. The ingest path then derives the presenting node's role from its TLS certificate CN (<role>.<fqdn>), rejects any message type illegal for that role (ERR_AUTH_ROLE), and de-duplicates by (sourceNodeId, seqNo) via a process-local ring — best-effort, explicitly not durable exactly-once. 2.2   solariServer internals & the solariCtl bridge

solariCtl is not a separate binary — it is a module compiled into solariServer (src/server/solariCtl.c) that listens on an AF_UNIX socket (default /run/solari/solariCtl.sock). It is the only way the dashboard mutates state. The protocol is line-oriented text:

# request / reply grammar (solariCtl.c)
request : VERB [k=v ...]\n
reply   : OK [k=v ...]\n  |  ERR <code> <message>\n

Destructive verbs (marked * in the verb table) require an op=<operator> attribution; DECOMMISSION additionally requires a two-step confirm=<token> handshake — the first call returns a token without acting. The same module holds the internal CA/CSR signing material (mbedTLS x509), so the PHP dashboard never holds a server certificate or CA key.

SECTION 03Subsystem container views

Four subsystems carry most of the system's behaviour outside the C core: the PHP dashboard, the notification pipeline, the SoR change-data-capture path, and the discovery/enrichment loop. Each is drawn here as a nested container view — process boundary, the containers inside it, and the trust edge each one crosses.

3.1   The PHP dashboard

The dashboard is a single Apache + PHP-FPM application with one front controller (dashboard/api/index.php) and a custom Router. Every request passes one chokepoint — Policy::enforce — which is default-deny: a route with no explicit grant is refused, and every non-GET additionally clears a CSRF synchronizer-token + Origin check before the handler runs (Phase-0 hardening, commits 2d74adf / 1812a9e). The SPA is vendored React + Babel-standalone; JSX is transpiled in the browser at load. There is no bundler and no package.json. php-fpm runs as the unprivileged user jason and reaches the C core only through the solariCtl UNIX socket — it never holds a certificate or a DB super-grant.

3.2   Notification & SoR-CDC pipelines

Two Python daemons in deploy/ bridge the fabric to the outside world over RabbitMQ. Neither is inside the C or PHP tiers — both are support glue, and both declare their exchanges defensively (there is no canonical broker config committed to the repo, a gap tracked below).

notify pipeline
solariServer's alert engine publishes to the durable topic exchange notify.events (vhost solari, amqp://…@10.5.2.50:5672/solari). notify.service / alertbridge.service consume and fan out to delivery channels (Apple push bridge, etc.).
SoR CDC
Writes to the SoR/CMDB DB fire sor_outbox triggers; sor-emit drains the outbox to the sor.events exchange; sor-apply-dns and sor-apply-pihole consume and reconcile DNS/Pi-hole. The reverse path (sor-reconcile) folds discovery back into the SoR.
Known gap — F-08

The CDC path can permanently lose events as built: publishes are not confirm-gated and consumers ack before applying. Phase-2 of the stabilization program adopts publisher-confirms, ack-after-apply, and a reconcile sweep. Until then, treat DNS/Pi-hole convergence from the SoR as eventually-consistent-at-best, not guaranteed.

SECTION 07Data model & System of Record

Two MariaDB databases, deliberately separate: a monitoring datastore that records what the fabric observes, and a System of Record that holds what the fabric is supposed to be. Discovery flows from the first into the second; DNS and Pi-hole flow out of the second.

7.1   Two databases

Monitoring DB
~30 InnoDB tables under db/migrations/001–019 — nodes, reports, probe results, alerts and rules, topology edges, discovery, panel/criticality, lifecycle tombstones. All timestamps stored UTC.
SoR / CMDB
Separate DB on cesium, mirrored to benzene. The canonical entity spine is defined in netdb/sor/schema.sql (netdb/sor/migrations/ holds only incremental deltas): entities, hardware_models, hardware_units, locations, networks, subnets, vlans, interfaces, ip_addresses. Change-data-capture rides a separate sor_outbox table defined in deploy/sorsync/sql/01-outbox.sql.
Known gap — F-12, schema lifecycle

The monitoring schema is not reproducible from a clean checkout as built: schema.sql is stale (reflects only migration 001), there is a duplicate ordinal 016 (two files, currently inert), and there is no single migrator with immutable IDs, checksums, and an applied-ledger. Phase-2 (I2) adopts one migrator and resolves the duplicate. Until then, the live database — not the tree — is the truth of what columns exist.

7.2   Provenance as a first-class column

The SoR distinguishes how it learned each fact: observed (seen by discovery), adopted (an operator promoted an observation to intended state), and authoritative (declared, the source of truth others reconcile to). The planned I2 track surfaces this provenance on every entity page, so the dashboard can never again present a discovered guess as a declared fact — the same honesty discipline that governs this document's OBS/INF flags.

SECTION 08Identity, authorization & trust boundaries

Authorization is enforced twice on the dangerous path — once in PHP before a command is formed, and again in C before it executes — and identity is derived from certificates on the wire, not from claims in a payload.

8.1   The human auth chain

A browser request is authenticated and authorized through four cooperating libraries before any handler runs. Local accounts use bcrypt; federated login uses Keycloak's OIDC authorization-code flow (confidential client), with Keycloak in turn federated to Samba AD over LDAPS. The legacy direct-LDAP path is a fail-closed stub — it denies rather than degrading open.

8.2   Machine identity on the wire

Machines do not authenticate with claims. Every SCP peer presents a client certificate whose CN encodes <role>.<fqdn>; the ingest path derives the role from the verified certificate and rejects any message type illegal for that role (ERR_AUTH_ROLE). The planned F-01 work makes the binding total — cert SAN/CN ↔ node ID ↔ role ↔ FQDN as one canonical identity contract, so a valid certificate can never be replayed under a different node's identity.

SECTION 09Developer workflow & build

One CMake tree builds the C tier; the dashboard has no build at all. The house rules are strict and load-bearing — they are why the system can be reasoned about.

9.1   Building the C tier

The control plane is ISO C99 built with CMake, wrapped by a thin top-level Makefile for convenience. Optional subsystems compile behind feature flags, so a minimal client can be built without the SQLite spool or the nng transport.

# from repo root — the Makefile just drives CMake
make            # configure + build all binaries into build/
make test       # run the C test suite (golden SCP frames, unit)

# feature flags (CMake cache):
SOLARI_WITH_IO=ON        # nng transport + reporter (solariNet.c)
SOLARI_WITH_SQLITE=ON    # client-side durable spool (solariSpool.c)

Wire compatibility is protected by golden-frame fixtures: canonical SCP frames are committed per protocol version and are immutable — a change that alters the bytes of an existing version fails the test rather than silently breaking older peers.

9.2   The dashboard has no build step

Hard house rule

There is no bundler, no package.json, no composer.json, and no Node.js anywhere in the runtime. OBSERVED — none of those files exists in the tree. React and Babel are vendored under dashboard/public/; JSX in screens*.jsx is transpiled in the browser at load. To develop the UI you edit a .jsx file and reload — there is nothing to compile. Introducing a build step into this code is forbidden by project policy, not merely discouraged.

9.3   Coding standards

Language
Standard C (K&R/ANSI) for the application; functional PHP 8+ for the dashboard; browser-only JS. No server-side JavaScript, ever.
Naming
camelCase is the house standard for variables, functions, and named structures across C and PHP alike — including where the language community would use snake_case.
Paradigm
Prefer functions to objects. Classes must earn their place with real shared-state invariants; the C core uses an opaque-handle pattern, not OOP emulation.
Comments
Every program, function, and non-obvious control structure carries a brief purpose / input / output statement. Explain intent and edge cases, not the obvious.

9.4   Tests & the CI gates being added

Dashboard authorization has PHP tests (tests/dashboard/test_authz_enforce.php, test_authz_dispatch.php) exercising the default-deny matrix and the request-method-to-verb dispatch. There is no phpunit or CONTRIBUTING in the tree yet. The stabilization program adds a battery of CI gates: a live-DB gate (SOLARI_TEST_DB=1), TLS-loopback + cert-identity failure tests, a generated route×method×role matrix with CSRF/Origin tests, submodule init before dashboard tests, migration clean-install / upgrade / idempotent-rerun checks, shellcheck/ASAN/UBSAN/fuzzers, and fault injection (broker loss, lease race, partial I/O, backup restore). A cross-lab review gate is required before committing to Phase-2 architectural choices — the original review was single-lab.

SECTION 10Operations & deployment

SolariNet is deployed as hardened systemd units driven from the deploy/ tree. This section covers how it runs, and — just as important — which capabilities are deliberately switched off.

10.1   Deployment layout

deploy/host-configs/
Per-host systemd units and Apache vhosts (e.g. xenon/solarinet-server.service, apache-solarinet.conf). Units are hardened (namespacing, restricted syscalls).
deploy/fleet/
Ansible inventory + a netboot catalog.json. The netboot HTTP service on benzene:8080 is staged and inert — see freeze below.
deploy/dns-bare/, netdb/
Zone generation from the SoT: gen-zones.py renders akoria.net; sync-net-to-org.py mirrors into the AD realm hourly; gen-bare.py produces the ~100 split-horizon per-host zones.
deploy/sorsync/
The CDC units — sor-emit, sor-apply-dns, sor-apply-pihole, sor-reconcile — running on xenon.

10.2   Frozen capabilities

Feature freeze — Phase 0 containment

The following are implemented but held Lab-only until their Phase-blockers close. They must not be enabled in production, and no new features may be built until Phase 4 gates pass.

  • Tab5 approvals — approval display not cryptographically bound to the approval (F-06/F-24).
  • One-button PXE provisioning — executes unauthenticated artifacts as root; key material left staged (F-07/F-16).
  • Arbitrary MCP SQL — replaced with fixed tools/views + a read-only account (F-18).
  • Opie automation — "read-only" model is not confidentiality-safe; sandboxed (F-15).
  • Remote CA automation — kept manual on chlorine.
  • LDAP/AD write paths beyond current use — frozen; AD is read-federated only.

10.3   Operational cautions

Before you act
  • Alarm tests are loud. The status-panel and alert paths drive real physical notification (LED panel on lithium, push bridges). A test alarm rings the actual fabric — announce it first.
  • Destructive verbs need attribution. DECOMMISSION, RETIRE, SIGN, DEPLOY, FLEET_*, and the *_REMOVE/_DEL verbs require op=; DECOMMISSION needs the two-step confirm-token.
  • Backups are not proven restorable. F-27 — nonempty ≠ restorable; a restore drill is Phase-3 work. Do not assume a backup will roll back a bad change.
  • DNS/AD apply has no rollback yet. F-17 — apply paths lack atomic switch + rollback semantics; a bad zone render is not automatically reversible today.

10.4   Health philosophy

The system's guiding operational rule, learned from the 2026-07-07 cesium incident (Forgejo served 500s for ~26 hours while a bare TCP check stayed green): a socket accepting a connection is not health. The host-health contract requires application-level liveness, and the planned freshness envelope {lastSuccess, ageSeconds, state} (I3) makes every page state its own staleness rather than presenting cached data as live.

SECTION 11Planned architecture & the stabilization program

An independent architecture review found that feature breadth had outrun enforcement and durability. The response is a declared feature freeze and a phased program with two goals: make the system honest and make it whole. Nothing new ships until it is done.

11.1   Two goals

Stability
"Done" means authorized and durably persisted and correctly delivered and actually applied and currently fresh — not merely "a socket accepted a message."
Integration
One entity spine, one freshness/health contract everywhere, one authorization matrix, consistent cross-navigation — pages and services tightly interlinked rather than parallel silos.
