What landed

Phase 5 (server) from §16 of the base plan and §5 of the Phase 3 Handoff is complete. The server is the persistent C2 tier: it terminates the SCP transport, ingests host/probe reports into MariaDB, arbitrates the primary/failover lease, and runs the §7.3 control plane (provision, decommission, adopt-target, enrollment, discovery). It is the first SolariNet binary to take a hard external dependency on a database — MariaDB Connector/C (libmariadb) — on top of the nng + mbedTLS transport already vendored in Phase 2.

The server is gated behind -DSOLARI_BUILD_SERVER=ON and is built only on the 64-bit tiers (x86_64 / arm64) where a database engine is expected to live; the zero-dependency core and the edge agents are unaffected.

Schema & migrations

The base schema (db/schema.sql) defines the §10 tables: node, hostCurrent, hostHistory, procCurrent, probeTarget, probeCurrent, probeHistory, serverLease, alertRule, alertEvent, nodeConfig. hostHistory and probeHistory use a TO_DAYS(sampledAt) RANGE partition scheme so retention can roll by month (the maintenance procedures land in Phase 7). Two forward migrations sit alongside it:

  • 001_baseline.sql — the §10 baseline as a versioned migration.
  • 002_c2_capabilities.sql — the Phase 3 Handoff §5 C2 tables, purely additive: segment, networkGear, lldpEdge, discovered, enrollment, buildArtifact, plus small column additions on node and probeTarget. No existing table changes shape.

Protocol §4 completion

Phase 5 also closed the remaining lifecycle protocol from §4: the SCP_MSG_DECOMMISSION message (0x32), the CTRL_PROVISION / CTRL_DECOMMISSION / CTRL_ADOPT_TARGET verbs, and the TLV_LIFE_CONFIRM / TLV_LIFE_WIPE_SCOPE TLVs. The Phase 4 monitor gained the matching CTRL_ADOPT_TARGET handler (src/monitor/monitorControl.c) so an adopted probe target is dispatched to the owning monitor. Decommission carries a one-time confirm token and an audit row — the same discipline the node-local executor enforces (see the Phase 7 decommission runbook).

The server suites follow the established single-.c-include pattern with a shared tests/unit/server_stubs.c, so the subsystem logic is exercised without a live database — the DB handle is stubbed at the seam.

Identical binaries, lease-decided role. Primary and failover run the same solariServer; the serverLease row is the single source of truth for who is active, so failover is a data decision, not a separate build — consistent with the §12.2 HA stance.

Build it yourself

./deploy/bootstrap-xenon.sh           # installs deps incl. libmariadb, builds, tests
# or directly:
cmake -S . -B build -DSOLARI_BUILD_TESTS=ON -DSOLARI_BUILD_SERVER=ON \
      -DSOLARI_WITH_IO=ON -DSOLARI_WITH_SQLITE=ON -DSOLARI_WITH_JSON=ON
cmake --build build && ctest --test-dir build --output-on-failure

Known gaps & deferred items

  • No live-MariaDB integration run here. The schema and migrations are authored to valid MariaDB syntax and reviewed, but they were not executed against a live MariaDB instance in this session. The unit suites cover subsystem logic with the DB handle stubbed; an end-to-end ingest-into-a-real-table run remains an operator acceptance step.
  • Topology depth (deep LLDP-MIB normalization, uplink-chain assembly) was completed in Phase 7, not here — see the Phase 7 report.
  • Retention / partition rolling (the procedures that exercise the TO_DAYS partition scheme) ship in Phase 7 under db/maintenance/.
