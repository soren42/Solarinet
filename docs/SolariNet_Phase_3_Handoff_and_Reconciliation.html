§ 0What this document is

This is the working handoff for the move from Phase 2 (libsolari I/O) to Phase 3 (client + platform layer), as development migrates off the macOS desktop and onto xenon, the dedicated AI-development system. It reconciles the code as it actually exists today against the base architecture plan, folds in the new C2 capabilities added during the dashboard work, and gives a coding agent an unambiguous worklist from here forward.

It extends the base spec (docs/SolariNet_Architecture_and_Plan.html); it does not replace it. Where this document and the base plan agree, the base plan remains the reference. Where they differ — new tables, new endpoints, new protocol verbs, the on-prem dashboard fix — this document wins, because it reflects decisions made after the base plan was written.

Reading order for the agent §1 (what's really done) → §2 (get building on xenon, verify Phase 2) → §3–§7 (the new architecture you'll implement) → §10 (the updated phase plan, your worklist) → §11 (housekeeping before first push). §§4–6 are the contract additions; treat them with the same authority as §§5/10/11 of the base spec.

1.1 What I verified on ingest (not taken on faith)

I rebuilt the dependency-free core directly with gcc -std=c99 -Wall -Wextra -Wpedantic -Werror=implicit-function-declaration and ran the unit suites that need no vendored libraries:

✓ test_crypto · test_tlv · test_frame · test_msg — all built clean (zero warnings) and passed

So the Phase 0–1 "all gates green" claim in docs/PHASE1_REPORT.html holds up independently. The three historical bugs that report mentions (CRC-32 polynomial typo, FNV offset basis, cert-CN trim) are fixed and covered by tests against published vectors.

1.2 What I could not verify here, and why that's expected

The Phase 2 translation units (solariNet.c, solariSpool.c, and the JSON-overlay path in solariConfig.c) are gated behind the CMake options SOLARI_WITH_IO, SOLARI_WITH_SQLITE, and SOLARI_WITH_JSON. They #include <nng/nng.h>, <mbedtls/…>, sqlite3.h, and cJSON.h — none of which are vendored in the archive (third_party/ holds only a minimal SQLite header shim and the Unity test framework). This is exactly the state the Phase 1 report predicted: the heavy libraries arrive in Phase 2, fetched by the bootstrap script. The code reads as correct and complete against the published APIs; it simply hasn't been compiled yet. Compiling and testing it is step one on xenon (§2).

§ 2Migration runbook: macOS desktop → xenon

The macOS box carried the project through the zero-dependency core. Phase 2's nng/mbedTLS/SQLite chain and Phase 3's Linux-first platform layer belong on the dedicated Linux dev host. The good news: the migration is almost entirely automated by a script already in the tree.

2.1 Why move now

  • Phase 2 needs the dep chain built natively. nng-with-TLS over mbedTLS is far less fiddly to build and test on Linux than on macOS, and xenon is where the system will actually run.
  • Phase 3 is Linux-first. platLinux.c is the reference platform implementation; it wants /proc, getifaddrs, raw sockets, and CAP_NET_RAW semantics that are native on xenon.
  • The macOS box still has a job. Keep it for building and smoke-testing platMacos.c when Phase 3 reaches the macOS PAL — cross-compilation and native macOS runs stay there. Primary development simply moves to xenon.

2.2 The runbook

  1. Get the repo onto xenon. Clone from github.com/soren42/Solarinet once it's pushed (§11), or rsync the working tree from the macOS box. Confirm git status is clean and you're on the intended branch.
  2. Run the bootstrap. ./deploy/bootstrap-xenon.sh. It is idempotent and safe to re-run. It detects the package manager (apt/dnf/yum), installs the build toolchain and dependency dev packages, and — crucially — falls back to building nng and mbedTLS from pinned source (NNG_TAG=v1.8.0, MBEDTLS_TAG=v3.6.2) when distro packages are missing. It then configures with -DSOLARI_WITH_IO=ON -DSOLARI_WITH_SQLITE=ON -DSOLARI_BUILD_TESTS=ON, builds, and runs the suites in two stages.
  3. Read the staged test output. The script splits results deliberately: the core + spool suites are a hard gate; the nng TLS loopback (test_net_loopback) is reported best-effort, so a transient port-in-use or a TLS-build wrinkle doesn't mask real success. If the loopback fails, that's your first Phase-2 debugging target — not a reason to proceed past it.
  4. Add cross toolchains when you need them. ./deploy/bootstrap-xenon.sh --with-cross pulls gcc-aarch64-linux-gnu, gcc-arm-linux-gnueabihf, and gcc-mingw-w64-x86-64 for the Phase 3 client matrix. Not needed until you're cross-building the client.
  5. Confirm the Phase 2 gate is green before touching Phase 3. The definition of done for the migration is: SOLARI_WITH_IO + SOLARI_WITH_SQLITE build clean and the transport loopback round-trips a frame over TLS. Capture that as a short Phase-2 completion note (mirroring the Phase 1 report style) so the milestone is recorded.
Verify, don't assume The script's pinned versions (nng v1.8.0, mbedTLS v3.6.2, SQLite 3.46.1, cJSON v1.7.18, Unity v2.6.0) are sensible and current as of the last edit. Before a long unattended source build, glance at whether mbedTLS has cut a newer 3.6.x patch — staying on the latest 3.6 LTS line is worth a one-line tag bump. Don't jump to mbedTLS 4.x without checking nng's compatibility; nng pins to the mbedTLS 3.x API.

2.3 Definition of done for the migration

  • Repo present on xenon, clean tree, builds with default options (core green).
  • bootstrap-xenon.sh completes; nng + mbedTLS available (packaged or source-built).
  • SOLARI_WITH_IO + SOLARI_WITH_SQLITE + SOLARI_WITH_JSON all compile clean.
  • Core + spool suites pass (hard gate); transport TLS loopback round-trips.
  • Phase 2 completion note written; tree committed.

§ 4Protocol additions (SCP)

The new capabilities need a small, backward-compatible extension to the SolariNet Control Protocol. All of it fits the §5 framing untouched — new message types and new TLVs only, so SCP_PROTO_VERSION does not bump (§5.9: adding message/TLV types is non-breaking; old peers skip what they don't understand).

4.1 New message types

TypeCodeDirectionPurpose
SCP_MSG_DISCOVERY_ADVERT new0x13node → serverA node reports entities it has observed but that aren't enrolled — neighbors from mDNS/ARP/LLDP, open service ports, new MACs. Feeds the discovery engine.
SCP_MSG_TOPOLOGY_REPORT new0x14node → serverLink-layer adjacency a node can see: its uplink switch/port from LLDP, peer reachability, interface→segment binding. Feeds the network-hierarchy view.
SCP_MSG_DECOMMISSION new0x32server → nodeAuthoritative teardown directive (see verb below). Distinct from CONTROL so it can never be confused with a routine config push and is always audited.

4.2 New control verbs (TLV_CTRL_VERB, extends §5.8)

VerbValueEffect on node
CTRL_PROVISION new7First-time bring-up: write config, install/enable the service unit, begin reporting. Idempotent — a re-provision converges to the supplied epoch.
CTRL_DECOMMISSION new8Carried by SCP_MSG_DECOMMISSION. Graceful: stop sampling/probing, flush & close the spool, securely erase local config, certs, keys, and spool DB, disable and remove the service unit, then exit. Replies CONTROL_RESULT (best-effort, before key deletion) so the server can mark the node retired.
CTRL_ADOPT_TARGET new9(Monitor) promote a discovered entity to a live probe target without a full redeploy — the "one-click monitor this" path from the Discovery screen.

4.3 New TLV types

/* --- discovery (0x12xx) --- */
TLV_DISC_ENTITY     = 0x1201,  /* repeated: {kind, host/ip, via, seg, arch} */
TLV_DISC_SERVICE    = 0x1202,  /* repeated: {proto, port, banner?}          */
TLV_DISC_SOURCE     = 0x1203,  /* uint8: 1=mDNS 2=ARP 3=SCP_advert 4=portscan 5=LLDP */
/* --- topology / LLDP (0x13xx) --- */
TLV_TOPO_UPLINK     = 0x1301,  /* {peerChassisId, peerPort, localIf, speedMbps} */
TLV_TOPO_LLDP_NEIGH = 0x1302,  /* repeated LLDP neighbor TLV set            */
TLV_TOPO_SEGMENT    = 0x1303,  /* {ifName, cidr, segHint}                   */
/* --- lifecycle (0x32xx) --- */
TLV_LIFE_CONFIRM    = 0x3201,  /* uint64: echo token the server must match  */
                                  /* to authorize a destructive decommission  */
TLV_LIFE_WIPE_SCOPE = 0x3202   /* bitfield: config|certs|spool|logs|unit    */
Destructive-op safety CTRL_DECOMMISSION requires a server-issued confirmation token (TLV_LIFE_CONFIRM) that the node echoes — a single stray frame can't wipe a host. The wipe scope is explicit (TLV_LIFE_WIPE_SCOPE) so "remove from monitoring but leave logs for forensics" is expressible. Every decommission writes an alertEvent-style audit row server-side (§5) before the node is marked retired.

§ 5Schema additions (MariaDB)

Six new tables and two small column additions extend db/schema.sql. They are additive — no existing table changes shape — so this is a forward migration, not a rewrite. Add as db/migrations/002_c2_capabilities.sql.

db/migrations/002_c2_capabilities.sql
-- network segments (first-class; referenced by node, gear, discovery)
CREATE TABLE segment (
  segId    VARCHAR(32) PRIMARY KEY,        -- "core","compute","storage","dmz","lab","iot"
  label    VARCHAR(64) NOT NULL,
  cidr     VARCHAR(64) NOT NULL,            -- e.g. "10.42.20.0/24"
  wireless BOOLEAN NOT NULL DEFAULT FALSE,
  notes    VARCHAR(255)
) ENGINE=InnoDB;

-- network gear (switches/APs/gateways) for the LAN-hierarchy topology
CREATE TABLE networkGear (
  gearId   VARCHAR(48) PRIMARY KEY,        -- "sw-core-01","gw","ap-lab-01"
  name     VARCHAR(96) NOT NULL,
  kind     ENUM('gateway','switch','ap','router','other') NOT NULL,
  model    VARCHAR(96), segId VARCHAR(32),
  ports    SMALLINT, uplinkGearId VARCHAR(48),  -- self-referential hierarchy
  wireless BOOLEAN NOT NULL DEFAULT FALSE, mgmtIp VARCHAR(64),
  lastSeenAt DATETIME,
  INDEX(segId), INDEX(uplinkGearId)
) ENGINE=InnoDB;

-- LLDP / inspection-derived adjacency: who connects where, at L2
CREATE TABLE lldpEdge (
  id          BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  nodeId      BIGINT UNSIGNED,                -- a SolariNet node, if the endpoint is one
  gearId      VARCHAR(48),                     -- the switch/AP side
  localIf     VARCHAR(48), peerPort VARCHAR(48),
  linkType    ENUM('wired','wireless') NOT NULL,
  speedMbps   INT, rssi SMALLINT, viaLldp BOOLEAN NOT NULL DEFAULT FALSE,
  observedAt  DATETIME NOT NULL,
  INDEX(nodeId), INDEX(gearId)
) ENGINE=InnoDB;

-- discovered-but-not-monitored candidates
CREATE TABLE discovered (
  discId    BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  host      VARCHAR(255), ip VARCHAR(64) NOT NULL,
  kind      ENUM('host','service','network','other') NOT NULL,
  via       ENUM('mdns','arp','scp_advert','portscan','lldp') NOT NULL,
  services  JSON,                            -- ["ssh:22","http:80"]
  segId     VARCHAR(32), arch VARCHAR(16),
  seenCount INT NOT NULL DEFAULT 1, firstSeenAt DATETIME, lastSeenAt DATETIME,
  status    ENUM('new','ignored','adopting','adopted') NOT NULL DEFAULT 'new',
  UNIQUE(ip, kind), INDEX(status), INDEX(segId)
) ENGINE=InnoDB;

-- pending enrollments (CSRs awaiting operator approval) — §15.1 made stateful
CREATE TABLE enrollment (
  enrId       BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  host        VARCHAR(255), ip VARCHAR(64),
  role        ENUM('client','monitor','server') NOT NULL,
  certFp      VARCHAR(95),                    -- SHA-256 CSR fingerprint, colon-hex
  status      ENUM('token','pending','approved','rejected','expired') NOT NULL,
  requestedAt DATETIME, decidedAt DATETIME, decidedBy VARCHAR(64),
  csrPem      TEXT,                          -- held only until signed, then nulled
  INDEX(status)
) ENGINE=InnoDB;

-- build/artifact registry (per arch/os/channel) + convergence rollup
CREATE TABLE buildArtifact (
  buildId   BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  arch      VARCHAR(16) NOT NULL, os VARCHAR(16) NOT NULL,
  version   VARCHAR(32) NOT NULL,
  channel   ENUM('stable','beta','dev') NOT NULL DEFAULT 'stable',
  sha256    CHAR(64) NOT NULL, sizeBytes BIGINT UNSIGNED,
  artifactUri VARCHAR(255), publishedAt DATETIME,
  UNIQUE(arch, os, version, channel)
) ENGINE=InnoDB;

-- small additions to existing tables (additive)
ALTER TABLE node     ADD COLUMN segId VARCHAR(32) AFTER arch,
                       ADD COLUMN uplinkGearId VARCHAR(48),
                       MODIFY state ENUM('up','degraded','down','unknown','retired') NOT NULL DEFAULT 'unknown';
ALTER TABLE probeTarget ADD COLUMN label VARCHAR(128), ADD COLUMN segId VARCHAR(32);

The retired state on node is what a completed decommission sets — the row is kept for audit/history rather than deleted, so the fleet's past is never silently rewritten. A nightly job may purge retired rows older than the retention window.

§ 7New server-side subsystems

The endpoints above are fed by four new server subsystems, each a C source file under src/server/ following the established handle/return-status conventions. They land in Phase 5 (server) and Phase 7 (the discovery/topology collectors that depend on monitor data), per the updated plan in §10.

7.1 Discovery engine — serverDiscovery.c new

  • Consumes SCP_MSG_DISCOVERY_ADVERT from clients and monitors; upserts discovered rows keyed by (ip, kind), incrementing seenCount.
  • Sources: clients report mDNS/ARP neighbors they can cheaply see; monitors add port-scan and SCP-advertisement findings; the topology collector contributes LLDP-seen-but-unenrolled devices.
  • Applies config.autoDiscover (gather vs. not) and config.autoEnroll (auto-issue enrollment vs. hold for operator) — both default conservative (discover yes, auto-enroll no).
  • De-dupes against the node table so already-monitored entities never appear as "new."

7.2 Topology / LLDP collector — serverTopology.c new

  • Consumes SCP_MSG_TOPOLOGY_REPORT; maintains networkGear and lldpEdge.
  • Node side: each client/monitor reports its uplink (LLDP chassis/port where the OS exposes it; falls back to ARP + switch inspection). Monitors additionally inspect managed gear (SNMP/LLDP-MIB) where reachable, populating networkGear.
  • Builds both projections for /api/topology: the monitoring hierarchy (from HRW assignment, already computable) and the network hierarchy (from gear + edges).
  • Scope note: deep managed-switch interrogation (full LLDP-MIB walks) is the most environment-specific piece. Start with what nodes self-report (their own uplink) — that alone yields a usable host→switch hierarchy — and treat exhaustive gear discovery as an enhancement.

7.3 Provisioning & lifecycle — serverProvision.c new

  • Owns the enrollment state machine (token → pending → approved/rejected) and CSR signing via the internal CA, through solariCtl.
  • Issues CTRL_PROVISION (bring-up), routine CTRL_SET_CONFIG/CTRL_DEPLOY (already in base), and CTRL_DECOMMISSION (teardown).
  • Decommission is the carefully-guarded path: generate a one-time confirm token, persist an audit row, emit SCP_MSG_DECOMMISSION, await best-effort CONTROL_RESULT, then set node.state='retired'. If the node is already offline, mark intent and complete the teardown when/if it returns, or let the operator force-retire (which only updates server records — the node, when wiped manually, simply never reconnects).
  • Tracks build convergence by joining buildArtifact against nodeConfig.appliedEpoch for /api/builds.

7.4 Probe-target adoption — monitorAdopt path new

The "monitor this discovered thing now" action: serverProvision.c resolves the discovered entity to a probe spec and sends CTRL_ADOPT_TARGET to the owning monitors (selected by the existing HRW logic, §8.2 of the base plan). No redeploy; the monitor adds the target to its live schedule. This reuses the monitor's existing scheduler — only a new control handler is required there.

§ 8Dashboard reconciliation

Claude Design delivered a React 18 C2 that transpiles in-browser via Babel-standalone — no Node build step, which keeps it inside the no-Node rule. Three screens are wired to mock data; five are scaffolded against the same mock. The work to make it real is wiring, not redesign. One issue must be fixed before it can run on the intranet.

8.1 Must-fix: on-prem / no-cloud

Blocks air-gapped operation index.html loads React, ReactDOM, and Babel from unpkg.com and fonts from fonts.googleapis.com at runtime. That violates the base plan's "local control, no cloud dependency" tenet and your standing no-phone-home preference — the C2 must work with no internet. Fix: vendor react, react-dom, and @babel/standalone into dashboard/public/vendor/ (the versions are already SRI-pinned, so just download those exact files), self-host the IBM Plex Sans/Mono woff2s under dashboard/public/fonts/, and repoint index.html at the local paths. Switch React to the production build while you're there. This is quick and unblocks everything else.

8.2 The wiring pattern (keep it; it's the right call)

The design exposes one global model, window.SOLARI, built by data.jsx (a seeded mock). The reconciliation doc Claude Design left in the tree (dashboard/API_RECONCILIATION.html) proposes — correctly — to add a single api.jsx adapter that fetches the §11.2 + §6 endpoints and populates the same shape, so every screen keeps working unchanged and data.jsx stays as the offline/demo fixture. All unit/time conversion (the UI thinks in % and "min ago"; the wire speaks KB/milli and ISO-8601) lives in that adapter via the existing SOLARI.fmt helpers. Build it once; light up screens against it incrementally.

§ 9The MCP integration

New since the base plan: integrations/mcp/ is a Python (FastMCP) server that gives an LLM agent read access to the dashboard API and the MariaDB schema, plus a guarded set of control actions. It's written in Python — not Node, per policy — with unit tests and an eval suite.

  • Three surfaces: the read-only §11.2 API, read-only SQL over the §10 schema (intended to run under a GRANT SELECT-only account), and the operator control plane (survey / config push).
  • Status: since the REST API (Phase 6) and live MariaDB aren't up yet, it targets the documented contract and is validated against an in-memory mock of both. Point it at the real deployment with environment variables only — no code changes, no secrets in files.
  • Reconciliation action: when the new §6 endpoints land, extend the MCP's tool set to cover discovery, provisioning, and topology reads. Keep the SQL guard's allow-list in step with the new tables (§5). The destructive control tools (decommission) must require the operator token and mirror the same confirm discipline as the dashboard.
