Architecture (firm invariants)

  • Application is strictly standard C + Makefiles/CMake; the dashboard is independent PHP.
  • PHP is read-only: SELECTs and local config/socket reads only. Every write/mutation goes through C via the solariCtl AF_UNIX bridge (run/solariCtl.sock).
  • solariCtl protocol: line-oriented VERB k=v …\n → OK [k=v]\n / ERR <code> <msg>\n; values URL-encoded; destructive verbs (e.g. SIGN, DEPLOY, DECOMMISSION) require an op= operator (RBAC).
  • Internal CA: issues leaf certs by signing CSRs (mbedTLS x509). The CA private key lives only in the server/CA process — never on the web tier, never in the deploy script. A modular [ca] config block (mode=local|remote + url) lets the CA relocate to a dedicated host later.
  • Transport: nng (PUSH/PULL ingest, REQ/REP control, PUB survey) over mutual TLS (mbedTLS).
  • DB: MariaDB solarinet, user solari. hostCurrent has an FK to node (a node must exist — via HELLO — before its report writes hostCurrent); procCurrent PK is (nodeId, procName).

Live deployment facts & hard-won gotchas

Dial the server by NAME, not IP. Older mbedTLS (2.28 — Debian bookworm, UniFiOS, many appliances) does not match IP-address SANs, so an IP server URL fails TLS there. remote-deploy.sh defaults to the server hostname (which is in the cert SAN) and pins name → server IP in the target’s /etc/hosts so it resolves regardless of LAN DNS. Server cert SAN currently: DNS:localhost, DNS:xenon, DNS:xenon.akoria.net, IP:127.0.0.1, IP:10.0.0.20.
  • glibc floor: build clients on debian:bookworm (glibc 2.36), not Ubuntu 24.04 (2.39) — a newer-glibc binary dies at launch (GLIBC_2.38 not found) on older targets.
  • Re-deploys must restart the service (not enable --now) or the old config/cert keeps running.
  • hole (10.0.0.254) is a Raspberry Pi (arm64, Debian bookworm) — enrolled and streaming telemetry.
  • zima* / 10.0.0.253 (ZimaOS) is not deployed: immutable Buildroot appliance — RO /usr,/etc,/opt; no apt; missing libnng/libmbedTLS/libcjson. The installer now refuses it with guidance. It needs the container path (Docker is present; /DATA/AppData is writable).

The adaptive installer (how to deploy)

# Build a portable client for an arch (Docker + qemu/binfmt; one-time:
#   sudo docker run --privileged --rm tonistiigi/binfmt --install arm64)
deploy/cross-build-client.sh arm64          # -> deploy/dist/arm64/solariClient
deploy/cross-build-client.sh x86_64         # -> deploy/dist/x86_64/solariClient

# Deploy + enroll + start (probes the target and adapts):
deploy/remote-deploy.sh --host jason@10.0.0.254 --op admin
#   --server tls+tcp://NAME:7701   (name must be in the server cert SAN; default = server hostname)
#   --server-ip IP                 (IP to pin NAME to; default = this host's LAN IP)
#   --remote-bin / --conf-dir      (override auto-probed writable dirs)
#   --dry-run                      (print the plan)

One SSH round-trip classifies the host — privilege (root vs sudo), arch, FQDN, init system, libc, package manager, writable dirs — and the deploy adapts: systemd · OpenWrt/procd · sysvinit · cron @reboot · bare nohup; apt · opkg · none; auto-chosen writable install dirs.

Outstanding issues & features (for the next session)

Heterogeneous-client roadmap (the active thread)

The fleet includes UniFiOS / Ubiquiti gear on arm64, x86, armv7, and at least one MIPS device, plus immutable appliances (ZimaOS). The agreed tiered plan; the adaptive installer (tier-1 plumbing) is done:

1 — Static-musl build matrix recommended next. Build fully-static binaries (vendored nng + mbedTLS + sqlite + cJSON, musl libc) for x86_64 / arm64 / arm32 / mips / mipsel — e.g. via zig cc. This is the prerequisite that makes MIPS/musl/library-less appliances actually run the agent, and bundling a modern mbedTLS would also retire the IP-SAN workaround. The installer already warns “musl + no pkg mgr → needs a static build.”
2 — Container agent for immutable-but-container hosts (ZimaOS): client image + a deploy path mounting host /proc + host net, config/cert on the writable data volume.
3 — Agentless poll (SNMP / SSH-exec / UniFi-controller API) for fully-closed devices that can’t run our binary — a separate “managed node” class in the model.
