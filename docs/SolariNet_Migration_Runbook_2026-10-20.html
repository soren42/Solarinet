SolariNet migration runbook

Candidate procedure · refreshed 23 October 2026 · monitoring DB and SoR

Production gate: Current live databases have no solari_migration_ledger. The runner intentionally refuses them. Do not stamp their history from table presence alone; audit a backup and compare the actual schema against every historical migration first.

1. What the runner does

tools/migrate.py applies full file IDs in order, including both distinct 016_* monitoring migrations. It stores each SHA-256 checksum and an applying / applied state in the target database. Before writing, it inventories tables, views, routines, and scheduled events; it refuses edited or missing historical files, gaps, interrupted runs, and schemas with objects but no ledger. MariaDB DDL is not transactional; an interrupted file requires inspection rather than automatic replay.

2. Clean installation

Create each new empty database with the canonical character set and collation using an account permitted to create databases. The runner checks this default before inventory or writes, because tables that inherit database defaults must be reproducible across MariaDB hosts. It refuses another default; it does not alter an existing database. Supply migration credentials through a protected MariaDB option file, a local Unix socket account, or a process environment managed outside git. Run from any directory; the script resolves SQL paths from its own location.

mariadb -e 'CREATE DATABASE NEW_MONITORING_DB CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci; CREATE DATABASE NEW_SOR_DB CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;'
python3 tools/migrate.py --database monitoring --db-name NEW_MONITORING_DB --check
python3 tools/migrate.py --database monitoring --db-name NEW_MONITORING_DB
python3 tools/migrate.py --database monitoring --db-name NEW_MONITORING_DB --check

python3 tools/migrate.py --database sor --db-name NEW_SOR_DB --check
python3 tools/migrate.py --database sor --db-name NEW_SOR_DB --defaults-file /path/to/protected.cnf

The final --check should show no PENDING files.

Regenerate reference snapshots

Each command creates a temporary database, applies the full ledgered stream, and writes a deterministic schema-only artifact.

python3 tools/export_schema.py --database monitoring
python3 tools/export_schema.py --database sor

Snapshot export requires permission to create and drop a temporary database. CI compares both snapshots with clean migration runs. Snapshots are reference artifacts only; install through the ledgered migrator. solariServer --init-db remains retired.

3. Existing databases and failure recovery

Live SoR connection recheck (2026-10-21; historical, superseded by the 2026-10-23 audit below): a read-only connection from Xenon through the deployed SoR sync service configuration reports Cesium MariaDB 12.3.2, 41 SoR base tables, 24 triggers, and no solari_migration_ledger. The query emitted schema metadata only; it did not read application rows or change the database. This confirms the existing adoption gate remains current.

Before preparing an adoption record, compare the current schema to the candidate snapshot with the read-only auditor. It makes no schema changes and excludes the runner's own ledger from the comparison:

python3 tools/audit_schema.py --database monitoring --db-name solarinet \
  --defaults-file /path/to/protected.cnf
python3 tools/audit_schema.py --database sor --db-name sor \
  --defaults-file /path/to/protected.cnf

An exact match compares tables, views, triggers, routines, and events, while normalizing account-specific definers and live next-ID counters. It verifies schema shape only. A unified diff identifies object-definition drift for review; it does not prove historical migration execution, validate data or grants, or approve stamping a ledger. This conservative comparison is expected to report differences for the currently documented production schemas.

  1. Back up the database and record the table, column, index, trigger, and view definitions. Confirm which migrations ran, including the two monitoring files numbered 016.
  2. Compare the actual schema with the full ordered file set. Resolve any drift through a reviewed forward migration. Only then prepare an explicit adoption record with matching immutable file checksums.
  3. If the runner reports applying, inspect which statements in that file committed. Repair or complete the partial DDL, then record the verified result. Do not delete a ledger row merely to retry the file.
  4. Re-run --check before applying pending files. Stop if the ledger checksum differs from the checked-out file.

4. Evidence and limits

This verifies fresh-install and repeat-apply behavior on the local MariaDB version; it does not authorize or validate adoption of the existing Xenon/Cesium schemas.

Observed in scratch databases (2026-10-21; historical): A fresh MariaDB 11.8.6 validation applied all 34 monitoring and the 8 SoR source files available at that date; clean rechecks produced no pending entries. The generated monitoring and SoR schema snapshots matched byte-for-byte, then restored into separate clean databases with identical table/view sets and SoR trigger set. Separate disposable MariaDB 11.8.6 runs matched both read-only audits, detected injected drift, and rejected wrong-collation databases before creating objects. Run local tool tests with python3 -m unittest discover -s tools -p 'test_*.py'. The fresh 2026-10-21 decommission test database is disposable scratch state.
