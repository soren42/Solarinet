Fleet Provisioning Subsystem

SolariNet Monitoring · automated OS install + provisioning + enrollment across distros and architectures · built 2026-06-26

What this is. A one-click path from the dashboard to a fully installed, configured, and SolariNet-enrolled machine — bare-metal x86 via netboot, Raspberry Pi via native netboot (Pi 5) or a prebuilt image (Pi 4), across Debian, Ubuntu, and openSUSE on x86_64 / arm64 / arm32, all with the same core software stack. Ansible + netboot infrastructure lives on benzene; the control plane stays in the existing SolariNet server + dashboard on xenon.

Architecture

The subsystem obeys the project's firm rule — PHP is read-only; every mutation goes through C via the solariCtl bridge. Two new operator-gated bridge verbs drive it:

VerbForksDoes
FLEET_PROVISIONdeploy/fleet/fleet-provision.shmints the node cert (SIGN), renders the distro's unattended-install config + a per-MAC iPXE entry, pushes them to benzene
FLEET_IMAGEdeploy/fleet/fleet-image.shmints the cert, builds a customized Raspberry Pi image on benzene

Both are detached (double-fork) so the server loop never blocks, and both require an op= operator (RBAC). The scripts run on xenon, mint certs against the local CA over the bridge (the CA key never leaves the server), and SSH to benzene to stage artifacts.

Dashboard (Provisioning → "Provision a new system")
   └─ POST /api/control/fleet-provision   (PHP: validate + marshal, read-only)
       └─ solariCtl FLEET_PROVISION       (C bridge, operator-gated, detached)
           └─ deploy/fleet/fleet-provision.sh   (on xenon)
               ├─ SIGN CSR → ca.pem/node.pem/node.key   (local CA)
               ├─ render netboot/configs/*.tmpl + ipxe/mac-profile → benzene HTTP root
               └─ stage per-MAC auto-install (inert until PXE is live)

Images & Stacks (SoR catalog)

OS images and software are SoR rows, not files: prov_images (distro → release → arch, boot method, source + checksum URLs, install template), the prov_software pool (pkg · repo · artifact · build · script · role, with per-family names, pins, per-arch artifacts, requires/conflicts) and prov_stacks (ordered pool references + stack dependencies; the locked core stack is always included and runs first). Dashboard → Images & Stacks edits all of it through /api/provisioning/* — structured forms, no YAML in the browser — and drives one Deploy per target:

ActionVerbDoes
Update (per image)IMAGE_REFRESHre-fetches the image on benzene, verifies every sha256, regenerates boot.ipxe
Deploy · ReimagePROV_STAGEstages the target's MAC against a fetched iPXE image; the chosen stacks apply at first boot
Deploy · Apply stacks onlySTACK_APPLYone Ansible run over SSH, no reimage; offered as a check-mode dry-run first

Every write is operator-gated and goes through the ctl request queue. Runs are audited in prov_runs, and the screen tails the helper log for each run (GET /api/provisioning/log). Stacks are resolved (closure + order) and rendered to Ansible vars at run time; the screen shows the same run order before you confirm. The old read-only catalog.json / /api/control/fleet-catalog reference data is retired.

The shared software stack (identical everywhere)

One logical package set in deploy/fleet/ansible/group_vars/all.yml (solari_core_packages) is applied on every distro and arch; a small solari_pkg_map translates the few names that differ between the Debian/Ubuntu and openSUSE families. Core set: sudo curl wget ca-certificates gnupg htop tmux git vim rsync jq unzip lsof chrony python3 net-tools openssh-server + the SolariNet agent. The same list feeds the Pi image build and legacy Debian/Ubuntu netboot installs staged without a run id; netboot installers otherwise carry only a minimal per-family bootstrap set (SSH server, sudo, curl, CA certificates, python3, one <package> per name on AutoYaST), and core arrives as the core stack after first boot. (This is the legacy OS install path; the Images & Stacks path takes its packages from the SoR core stack instead.)

Netboot activation runbook (done — Option B is live)

Kept for reference / re-activation. Bare-metal machines only netboot once DHCP tells them where the boot server is. Use one of these; both coexist with the existing gateway DHCP. The live network uses Option B.

Option A — proxyDHCP on benzene (self-contained, reversible)

A dedicated dnsmasq in proxy mode answers only PXE boot requests; it never hands out IP leases, so it does not conflict with the gateway's DHCP.

First make sure every installer you intend to boot is fetched and verified: run the operator-gated IMAGE_REFRESH verb for each iPXE image row (the image row's Update button in Images & Stacks, i.e. POST /api/provisioning/image-refresh {"image": <id>}). It downloads the kernel/initrd on benzene, checks every sha256 against the upstream checksum source, writes solari-image.json, and regenerates boot.ipxe. fetch-images.sh is now only the internal worker of that verb — it has no built-in URL list and no --distro all mode.

# then flip PXE live on benzene:
/srv/solari-provision/staging/go-live.sh          # enable + open firewall
/srv/solari-provision/staging/go-live.sh --off    # fully reverse it

Option B — UniFi DHCP options (no responder on benzene)

Add these to the DHCP scope in the UniFi controller (Network → the LAN → DHCP), then leave benzene's responder disabled:

Network boot / PXE:
  Enabled:      yes
  Server (next-server):  10.5.2.50        # benzene
  Filename (BIOS):       pxelinux.0
  Filename (UEFI x64):   ipxe-x86_64.efi
  Filename (UEFI arm64): snp-arm64.efi
# iPXE then chains to  http://10.5.2.50:8080/ipxe/boot.ipxe
Network-safety note. Do not run a second full DHCP server on the flat 10.0.0.0/8 — only proxyDHCP (Option A) or the existing UniFi scope (Option B).

Provisioning flows

Bare-metal x86 (Debian / Ubuntu / openSUSE)

  • Dashboard → Provisioning → Provision a new system → "OS install", pick distro/arch/role, enter the target's MAC and a hostname → Stage install.
  • The installer image for that distro/release/arch must already be fetched + verified (IMAGE_REFRESH, above). FLEET_PROVISION refuses to stage a MAC against an unfetched image and stages nothing; refresh the image, then stage again.
  • The machine auto-installs unattended on its next network boot (per-MAC iPXE profile), runs the common package stack, and enrolls into SolariNet. An un-staged machine is never touched (the per-MAC chain 404s and it boots local disk).

Raspberry Pi

  • Pi 5 — native netboot (TFTP/HTTP root served from benzene); scaffold with deploy/fleet/pi/pi5-netboot/. Gated behind the same PXE switch.
  • Pi 4 — dashboard "Pi image" mode builds a customized Pi OS image (hostname, SSH key, core stack, SolariNet firstboot enrollment). Download from http://benzene:8080/images/<host>-<arch>.img and flash to SD/USB. Fully working today, no PXE needed.

Security model

  • Both verbs are operator-gated (RBAC); PHP validates every field and holds no CA material.
  • Node certs are minted on xenon via the bridge SIGN — the CA private key never leaves the server process, never touches benzene or the deploy scripts.
  • Enrollment material is staged under an unguessable per-host token dir (…/enroll/<random>/) and is not directory-listed; it should be removed after the node's first boot. Follow-up: replace with a one-time pull token for defence in depth.
  • Installed hosts get key-only SSH (password auth disabled, admin account with a locked password + the operator's public key).

Outstanding / follow-ups

  • Boot a real target through Images & Stacks to validate an unattended install end-to-end (P6: steel → openSUSE Tumbleweed + core). The final bare-metal wipe step is still untested on hardware.
  • Installer source/checksum URLs live on each prov_images row and may need adjusting as releases move; a failed checksum makes IMAGE_REFRESH refuse, leaving the previous image in place.
  • arm64 non-Pi netboot installers, and arm32/mips static agent builds, are future work (see the heterogeneous-client roadmap).
  • Enrollment auto-delivery hardening (one-time token) as noted above.
