Two ways in: a local admin account, or Sign in with Keycloak — your AD identity on akoria.org. Domain Admins map to dashboard admin; everyone else read-only.

What each area is for

Assets / Inventory

The live CMDB view. Every discovered + adopted host, its IPs, OS, role, and monitoring state. This is the human face of the System of Record.

Discovery

Newly-seen hosts on the network (nmap/mDNS sweep). You Adopt the ones worth tracking — that promotes them into the SoR and starts monitoring them.

Monitoring / Health

~49 targets, app-layer aware: not just ping, but real LDAP / MySQL / AMQP / DNS / HTTP checks on the infra that matters.

Topology

Combined network + monitoring map — nodes, interconnects, and their health, from real LLDP-over-SNMP.

Host health & alerts

Every client reports host-local telemetry each cycle — fs-readonly, missing block devices, SMART, failed systemd units, dmesg-critical lines — independent of whatever app is running there. fs-readonly / missing-device / SMART-fail are crit, sustained immediately (no debounce); failed-units and dmesg-crit are warn. A dead-man's-switch also watches the monitor itself: a node silent past 3× its sample interval pages on its own.

The one thing to understand

The dashboard writes the System of Record, and the SoR drives everything else — automatically. You never hand-edit a zone file, a Pi-hole list, or AD again. Make the change once, in the dashboard, and it fans out.
Dashboard edit → SoR (MariaDB, cesium) → CDC outbox → sor.events (RabbitMQ) → appliers fan out to:
BINDakoria.net forward/reversexenon · auto rndc reload on real change
Active Directoryakoria.orgradium · safe deletes (never touches AD infra records)
Pi-holehelium + mercury custom.listreload on change

And the reverse: a host you Adopt in Discovery flows the same way — into the SoR, then out to DNS — with no extra step.

Common tasks

Add a host to DNS

  1. Find it in Discovery (or add in Assets).
  2. Click Adopt / set its name.
  3. Done — A + PTR appear in akoria.net within seconds; AD + Pi-hole follow.

Rename or remove a host

  1. Edit the name (or Remove) in Assets.
  2. SoR updates; DNS re-renders and reloads automatically.
  3. Removal soft-deletes → record drops from all three DNS targets.

Start monitoring a service

Adopt with the ports you care about. Ports 389/3306/5672 auto-upgrade from a bare TCP check to a real LDAP / MySQL / AMQP app-layer probe. CLI equivalent:

ADOPT disc=<id> services=389,3306 heartbeat=1 → run/solariCtl.sock

Get alerts

Alerts publish to notify.events and fan out by severity:

infolog + MQTT only (quiet)
warn+ Apple (iMessage → all your devices)
crit+ Apple

Apple channel relays via hydrogen → iCloud → iPhone/iPad/Watch/Mac.

If something looks off

Is the pipeline flowing?

On xenon:

systemctl is-active sor-emit sor-apply-dns sor-apply-pihole sor-reconcile notify

On radium (AD applier lives here):

systemctl is-active sor-apply-ad

Did a change reach DNS?

dig +short <name>.akoria.net @xenon

dig +short <name>.akoria.org @radium

Appliers are idempotent + self-reconcile (AD hourly), so drift self-corrects.

Is a host actually healthy?

Port-open isn't healthy (see the cesium incident). Check the per-host telemetry in Assets → host, or the underlying columns on hostCurrent (fsReadonlyCount, blockDevMissing, smartFailCount, failedUnitCount, dmesgCritCount). A real host-fault alert lands on your Apple devices via iMessage as crit/warn with the metric + detail in the body (e.g. fsReadonly: /data (ro)) — same channel as any other alert, plus a synthetic node <X> stopped reporting if the host goes silent instead of erroring.

Credentials never live in the repo. They're in /root/.*-pw on each host (and private agent memory). If a doc or config shows a password, that's a bug — tell me.
