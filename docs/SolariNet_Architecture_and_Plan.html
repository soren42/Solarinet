§ 0How to use this document

This is a complete, self-contained build specification. An autonomous coding agent should be able to implement the entire system from this document with no further design input.

The document proceeds from strategy (why) to architecture (shape) to scaffolding (exact headers, signatures, schema, build files) to a phased task plan (the worklist). Read it in order once; thereafter §§5–12 are the implementation reference and §16 is the execution checklist.

Agent instructions Implement strictly in C99 using only functions and plain structs — no C++, no object orientation, no opaque OOP emulation beyond the documented handle pattern. Honor the coding standards in §17 (camelCase identifiers, K&R brace style, doc-comment headers). Build each module behind its published header (§§6–9) so components remain independently testable. Where a function body is not given, the signature plus its doc-comment is the contract — implement to it. Do not introduce Node.js, server-side JavaScript, or any npm-based tooling anywhere in the toolchain. The only non-C runtime is PHP 8.x for the dashboard (§11), reading the same MariaDB the server writes (§10).

The dashboard's visual design is intentionally out of scope here — it is produced separately in Claude Design. §11 specifies only the data contract (REST/JSON endpoints, auth, payload shapes) the dashboard binds to, so the two efforts compose cleanly.

§ 1Strategy & design tenets

SolariNet observes a private network (an intranet of roughly 60 devices) from three vantage points and fuses their views into one authoritative, continuously-published picture of health.

The three vantage points

Each tier answers a different question, and no single tier can answer all three — which is precisely why the system is distributed:

TierVantageAnswersVolume
Client solariClientInside the host, looking down"Is this machine healthy? CPU, RAM, swap, disk, NIC/USB throughput, key processes, their open files & sockets, log files."One per host, plus a watchdog
Remote Monitor solariMonitorOn the wire, looking across"Are services reachable and fast from where I stand? TCP/UDP/ICMP probes, latency, transit time, dropped packets, throughput vs. capacity, link characteristics, peer-to-peer reachability."~10% of nodes, at varied vantage points
Server solariServerAbove all, fusing"What is the whole-network state, historically and now? Collects client + monitor data, owns master records, publishes the C2 dashboard, manages config & deployment of every node."One primary, one failover

Design tenets

  1. Portability is a first-class requirement, not a retrofit. The client must build for Windows, macOS, and Linux across ARM32/ARM64/x86/x86_64. All OS-specific code lives behind a single platform-abstraction header (platOS.h); the core never calls a syscall directly.
  2. Fault tolerance by construction. Monitors are interchangeable and redundant — losing one degrades coverage, never correctness. The server runs primary/failover with a database-mediated lease, so a primary failure is a sub-30-second promotion, not an outage.
  3. One wire protocol, versioned from day one. Every tier-to-tier message rides the SolariNet Control Protocol (§5): a versioned, length-prefixed frame with a binary header and TLV payload. New fields never break old peers.
  4. The C backend never renders HTML. The server writes MariaDB; PHP-on-Apache reads it. This keeps the C strictly to measurement, transport, and persistence, and lets the dashboard evolve independently.
  5. Local control, no cloud dependency. Every component runs on-prem. No telemetry leaves the intranet. TLS and node enrollment are self-managed.
  6. Functions, not objects. Plain C, K&R lineage. State travels in explicit context structs passed by pointer (the "handle" pattern, §17) — never hidden in globals, never wrapped in pseudo-classes.

Non-goals

  • Not a public-internet, multi-tenant SaaS. Single-tenant, single intranet, trusted-ish LAN with TLS for defense in depth.
  • Not a metrics time-series database competitor (Prometheus et al. already exist in the environment). SolariNet's edge is the fused three-vantage view and the C2 control plane, not raw TSDB throughput.
  • Not a config-management replacement. The server's "manage config/deployment" role pushes SolariNet's own node config and binaries, not general-purpose CM.

Data flow

  1. Client → Server (push). Each client samples local metrics on a schedule (default 15 s) and pushes an SCP_MSG_CLIENT_REPORT frame to the server's ingest endpoint. Watchdog supervises the client process and emits SCP_MSG_WATCHDOG heartbeats independently.
  2. Monitor → Server (push + survey). Monitors run their probe schedule autonomously and push SCP_MSG_MONITOR_REPORT frames. The server can also actively survey the monitor fleet (nng SURVEYOR/RESPONDENT) to demand an immediate round, e.g. on operator request from the dashboard.
  3. Server → MariaDB. The active server validates, deduplicates, upserts master records, appends history rows, and evaluates alert rules.
  4. Dashboard → MariaDB. PHP reads via PDO. The C server and PHP never talk directly; the database is the contract boundary.
  5. Server → nodes (control, down). Config changes and binary/deploy directives flow as SCP_MSG_CONTROL frames addressed to specific nodes.

Failover model

Two server instances, exactly one active. Coordination is database-mediated to avoid pulling in a consensus library for a two-node problem:

  • A single row in the serverLease table holds (leaseHolder, leaseEpoch, expiresAt).
  • The active server renews the lease every leaseRenewSec (default 5 s) via a conditional UPDATE … WHERE expiresAt < NOW() OR leaseHolder = me inside a transaction. The atomicity of that single-row update is the election.
  • The standby polls the lease. If it observes expiresAt < NOW(), it attempts to claim it with an incremented leaseEpoch. Winner becomes active and begins binding ingest sockets; loser backs off.
  • Nodes always know both server addresses (from config); they connect to whichever currently holds the lease, discovered via a tiny SCP_MSG_WHO_IS_PRIMARY query answered by either instance.
Why DB-lease, not Raft For N=2 servers sharing a MariaDB they already depend on, a leased single-row mutex gives correct single-writer semantics with zero extra dependencies and trivial debuggability. Raft/etcd would add an operational component to babysit for no benefit at this cardinality. Split-brain is bounded by lease TTL and made harmless because all writes funnel through the same row's conditional update. If the fleet ever needs ≥3 active coordinators, revisit — but that is explicitly a non-goal (§1).

Security model

  • Transport: All SCP traffic is TLS 1.2+ via nng's TLS transport backed by mbedTLS. Plaintext SCP is permitted only on loopback (client ↔ its own watchdog) and only when explicitly configured.
  • Node identity & enrollment: Each node carries a long-lived X.509 client certificate issued at enrollment. Enrollment is a one-time operator-approved exchange: a node presents a pre-shared enrollment token (out-of-band), the server signs its CSR, and the node thereafter authenticates by cert. This dovetails with the operator's existing internal CA (step-ca) — the server's trust store is simply the internal CA root.
  • Authorization: A node's certificate CN encodes its role (client / monitor / server); the server rejects frames whose type is illegal for the presenting role (a client may not send SCP_MSG_MONITOR_REPORT, etc.).
  • Dashboard: Operator auth at the PHP layer (session + RBAC). The dashboard is read-mostly; any control action (trigger survey, push config) is POSTed to the REST API, authenticated, and translated by a small privileged helper into an SCP_MSG_CONTROL to the server. The PHP layer never holds a server certificate directly — it calls a local solariCtl Unix-socket helper that does.

§ 5The SolariNet Control Protocol (SCP)

One versioned, length-prefixed binary protocol carries every tier-to-tier message. A canonical JSON projection exists for any consumer that reads SCP data without speaking it natively (the dashboard, debugging tools).

5.1 Framing

Every SCP message on the wire is a single frame. nng delivers messages atomically, so the outer length prefix is redundant over nng but is retained so the format is self-delimiting over raw streams (spool files, loopback plaintext, packet captures).

  /* All multi-byte integers are big-endian (network byte order). */

  +----------------+----------------------+--------------------------+--------+
  | uint32 frameLen| FrameHeader (32 bytes)| TLV payload (frameLen-32)| uint32 |
  | (payload bytes)|                       |                          |  crc32 |
  +----------------+----------------------+--------------------------+--------+

  frameLen   = byte count of [FrameHeader + TLV payload]  (excludes itself & trailing crc32)
  crc32      = CRC-32 (IEEE) over [FrameHeader + TLV payload], integrity check only

5.2 Frame header (fixed 32 bytes)

include/solari/solariFrame.h — wire header
typedef struct {
    uint8_t  magic[2];      /* {'S','N'} — SolariNet sentinel              */
    uint8_t  protoVersion;   /* SCP_PROTO_VERSION; bump only on breaking chg */
    uint8_t  msgType;        /* enum solariMsgType (5.4)                     */
    uint8_t  flags;          /* SCP_FLAG_* bitfield (5.3)                    */
    uint8_t  reserved;       /* 0; keeps following fields aligned            */
    uint16_t tlvCount;       /* number of TLV elements in payload            */
    uint64_t sourceNodeId;   /* stable 64-bit node id (5.5)                  */
    uint64_t sendTimeUnixMs; /* sender clock, ms since epoch                 */
    uint32_t seqNo;          /* per-source monotonic; dedup & ordering        */
    uint32_t correlationId;  /* echoes a request's seqNo in its reply; 0 if  */
                              /* unsolicited                                  */
} solariFrameHeader;          /* sizeof == 32, statically asserted            */
Implementation note Do not memcpy the struct onto the wire — pack/unpack field-by-field through the accessor functions in §6 so endianness and alignment are correct on every architecture. A SOLARI_STATIC_ASSERT(sizeof(solariFrameHeader)==32) guards the layout, but the wire form is defined by the pack functions, not the struct memory image.

5.5 Node identity

sourceNodeId is a stable 64-bit id derived once at enrollment: FNV-1a-64(hostFqdn || roleByte || enrollmentNonce), persisted in the node's config. It is independent of IP/MAC so it survives re-addressing. The mapping nodeId ↔ (fqdn, role, cert CN) lives in the server's node table (§10).

5.6 TLV payload

Payloads are sequences of Type-Length-Value triples. This is what lets the protocol evolve without version bumps: unknown TLV types are skipped, not fatal.

5.7 Probe-result value layout (TLV_PROBE_RESULT)

typedef struct {
    uint8_t  proto;        /* 1=ICMP 2=TCP 3=UDP                      */
    uint8_t  outcome;      /* enum probeOutcome: ok/timeout/refused/… */
    uint16_t dstPort;      /* 0 for ICMP                              */
    uint8_t  dstAddr[16];  /* IPv4-mapped or IPv6                     */
    uint32_t rttMicros;    /* round-trip time, microseconds           */
    uint32_t jitterMicros; /* inter-probe variance                    */
    uint16_t lossPermille; /* packets lost per thousand               */

5.9 Versioning rules

  • Adding a TLV type → no version bump. Old peers skip unknown TLVs.
  • Adding a message type → no version bump if unsolicited and ignorable; receivers reply SCP_MSG_ERROR/ERR_UNKNOWN_MSG for types they must understand.
  • Changing header layout or an existing TLV's semantics → bump SCP_PROTO_VERSION. The server supports the current and previous major version during rollout.

§ 8Component: Remote Monitor solariMonitor

Distributed, interchangeable, fully redundant. Each monitor connects to TCP/UDP/ICMP endpoints of services and peers across the intranet, measuring reachability, response time, and link characteristics — then reports to the server. Targets Linux across the full architecture array; redundancy is by replication, not coordination.

8.1 Responsibilities

  • Service probing: for each configured target, run TCP connect / UDP echo / ICMP echo probes, recording RTT, jitter, packet loss permille, throughput vs. capacity, and outcome (ok/timeout/refused/unreachable).
  • Stationary service metadata: where a probe can cheaply learn it, capture service version/vendor/config banners (the "stationary" metadata in the brief).
  • Peer & network-wide metrics: peer-to-peer reachability among monitors, transit time, bandwidth vs. capacity, connection speed, overhead, dropped packets.
  • Report & survive: push SCP_MSG_MONITOR_REPORT; spool on failure; answer server SCP_MSG_SURVEY on demand.

8.2 Redundancy & fault tolerance model

Monitors are stateless w.r.t. each other except for a lightweight peer registry. The design goal — "interchangeable, fully redundant" — is met by overlapping assignment, not by leader election:

  • The server assigns each probe target a replication factor (default 2). Targets are distributed across the monitor fleet by rendezvous (HRW) hashing of (targetId, monitorNodeId), so each target is independently probed by its top-k monitors.
  • If a monitor drops out, the HRW ranking simply re-selects the next monitor for affected targets on the next schedule tick — no failover handshake, no split-brain.
  • The server deduplicates overlapping reports and treats divergence between vantage points as signal (e.g., target reachable from monitor A but not B localizes a network partition).
  • Monitors exchange a tiny peerAlive gossip so each knows the live fleet membership for HRW; the server is the source of truth and corrects drift via WELCOME/CONTROL.
Why HRW (rendezvous) hashing It gives consistent, low-churn target→monitor assignment with no coordinator and trivial recomputation when membership changes — exactly the property needed for "interchangeable and redundant." A monitor leaving reassigns only its targets; everyone else is untouched. This is materially simpler and more robust than consistent-hash rings or an elected scheduler for a fleet this size.

§ 11Dashboard data contract (PHP / Apache)

The visual design is produced separately in Claude Design. This section fixes only what the C system guarantees and what the dashboard may rely on, so the two compose without renegotiation. PHP reads MariaDB via PDO; control actions round-trip through solariCtl.

11.1 Architecture

  • Read path: PHP 8.x reads current/history tables via PDO (prepared statements only). No PHP writes to monitoring tables — those are the C server's exclusively.
  • Live updates: browser polls the JSON API (default 5 s) or subscribes to a Server-Sent Events endpoint (/api/stream) that the PHP layer feeds from the server's PUB socket via the solariCtl bridge. (SSE, not WebSockets — no Node, no long-lived PHP worker beyond a simple bridge.)
  • Control path: operator POSTs (e.g. "survey now", "push config") authenticate at PHP, then PHP calls solariCtl over its Unix socket; the helper emits the SCP control frame. Cert material never enters the web tier.

11.3 Auth & RBAC

  • Session-based login (PHP sessions, Argon2id password hashing). Optional reverse-proxy SSO if the operator fronts it.
  • Two roles: viewer (all GET) and operator (GET + control POSTs). Role checked server-side on every control endpoint.
  • CSRF tokens on all POSTs; control POSTs additionally re-verified by solariCtl before any SCP frame is emitted.

§ 15Deployment & operations

15.1 Enrollment flow (one-time per node)

  1. Operator generates an enrollment token on the server (short-TTL, single-use), delivered out-of-band.
  2. Node generates a keypair + CSR, presents token + CSR to the server's enrollment endpoint.
  3. Server (using the internal CA / step-ca root) signs the cert with a CN encoding role + FQDN, registers the node row, returns the signed cert + CA root.
  4. Node persists cert/key/CA, computes its nodeId, writes it to config, and connects normally thereafter.

15.2 systemd units (Linux)

deploy/systemd/solari-client.service

The watchdog is spawned by the client itself (§7.3), so systemd supervises the client and the client supervises its watchdog — defense in depth without a second unit. The monitor unit is analogous but adds CAP_NET_RAW for ICMP. Two server units (solari-server.service) run on the primary and failover hosts; both start identically and sort out active/standby via the lease.

15.3 Upgrade / deploy

Operator stages a new binary; server issues CTRL_DEPLOY (with SHA-256) to a node, which fetches, verifies, and stages it, then CTRL_RESTART triggers a watchdog-mediated re-exec. Rollout is staged (canary node → cohort → fleet) and tracked via nodeConfig.appliedEpoch convergence visible on the dashboard.

§ 17Coding standards

  • Language: ISO C99, functions only. No C++, no OOP emulation beyond the documented opaque-handle pattern (a typedef struct foo foo; with create/use/destroy functions). No global mutable state; thread state travels in context structs passed by pointer.
  • Naming: camelCase for functions, variables, struct fields, and typedef'd types; UPPER_SNAKE for macros and enum constants; module-prefixed public names (solariFrameParse, platCpuLoad, monitorOwnsTarget). Descriptive but not unwieldy.
  • Brace style: K&R (opening brace on the same line; else cuddled). Four-space indent, no tabs in C.
  • Returns & errors: functions return solariStatus; out-params written only on success unless documented. No errno-style hidden state across the API. Every error path logs at an appropriate level and propagates a code from Appendix A.
  • Memory: explicit ownership documented in each function's doc-comment; matching *Open/*Close, *Init/*Destroy pairs; zero-copy reads alias caller buffers and say so.
  • Doc-comments: every public function has a block comment stating purpose, ownership/lifetime of pointers, success/failure semantics, and platform notes where relevant (as shown throughout §§6–9).
  • Portability: no syscalls outside the PAL; fixed-width <stdint.h> types on the wire; never assume endianness or struct padding — pack field-by-field.
  • Git: conventional-commit style messages; the monorepo lives in a local git repo, with publishable components mirrored to GitHub at the operator's discretion.

Appendix C — ICMP portability notes

ICMP echo needs either a raw socket (root / CAP_NET_RAW) or, on Linux, the unprivileged SOCK_DGRAM/IPPROTO_ICMP path gated by net.ipv4.ping_group_range. probeRun tries, in order: (1) SOCK_DGRAM ICMP if the gid is permitted; (2) raw socket if the process holds CAP_NET_RAW (the monitor systemd unit grants it ambiently); (3) otherwise records PROBE_UNREACHABLE with a diagnostic detail rather than crashing. Since the monitor targets Linux only, the macOS/Windows ICMP idiosyncrasies don't apply to it; the client never sends ICMP.
