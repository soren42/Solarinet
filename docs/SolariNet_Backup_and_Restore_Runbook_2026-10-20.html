2. Runner behavior and tests

deploy/backups/solari-backup.sh requires a root-owned mode 0700 target, writes root-owned mode 0600 artifacts through unique checked temporary files, verifies the gzip stream contains SQL, and renames the finished artifact into place. It can run mysqldump under an optional local Unix account for socket authentication. Failure leaves an existing dated artifact untouched and triggers solari-notify-failure@HOST.service, which publishes a fail-soft warning through the configured notifier exchange. Retention removes only matching database dump names.

Configuration and credentials are root-owned with mode 0600. Keep passwords and credential paths out of Git. The templated systemd timer runs nightly at 03:30 with jitter; configure one instance per host. Forgejo dumps are optional and must be restored with repository/filesystem state from the same restore point.

sudo -n python3 -m unittest discover -s deploy/backups -p 'test_*.py' -v
sudo systemctl status solari-backup@cesium.timer
sudo systemctl list-timers --all solari-backup@cesium.timer

The hermetic suites exercise a valid compressed dump, empty-output rejection, refusal of a world-accessible target, dump execution as an unprivileged account, failed-dump preservation, Forgejo temporary-directory cleanup, atomic publication, safe retention, durable failure-event publication, missing-Pika fallback, and credential-safe error logging.

3. Configure a host

  1. Choose a durable target with enough free space and a recovery path independent of the database volume. Create it as root mode 0700. Confirm filesystem, mount persistence, server-side access controls, ownership, and monitoring before enabling the timer.
  2. Install the runner and unit files from deploy/backups/. Copy backup.conf.example to /etc/solari-backup-HOST.conf, set that host's database list and target, then set root ownership and mode 0600.
  3. Use a root-readable password file, protected environment file, MariaDB defaults file, or a local Unix account with socket authentication via MYSQLDUMP_RUN_AS. Never place credential material in the config example or command history.
  4. Run the backup service once, verify the dated artifact, validate its gzip stream, and restore it into a disposable database before enabling the recurring timer.
  5. Enable the timer and verify its next run. Monitor failure notifications and target capacity; a scheduled timer alone does not prove a usable backup exists.
sudo install -d -m 0755 /opt/solari-backups
sudo install -m 0755 deploy/backups/solari-backup.sh /opt/solari-backups/solari-backup.sh
sudo install -m 0755 deploy/backups/solari-notify-failure.py /opt/solari-backups/solari-notify-failure.py
sudo install -m 0644 deploy/backups/solari-backup@.service deploy/backups/solari-backup@.timer deploy/backups/solari-notify-failure@.service /etc/systemd/system/
sudo install -o root -g root -m 0600 /dev/null /etc/solari-notify-failure-HOST.conf
sudo $EDITOR /etc/solari-notify-failure-HOST.conf
sudo systemctl daemon-reload
sudo systemctl start solari-backup@HOST.service
sudo systemctl enable --now solari-backup@HOST.timer

The example targets Cesium's sor database and /data/backups, observed root-owned mode 0700. Xenon's candidate off-host target is the dedicated SolariNetBackups directory under Jason's NAS-X personal share, mounted at /mnt/solari-backups. The candidate files are deploy/backups/backup.conf.xenon.example, deploy/backups/mnt-solari\x2dbackups.mount, and the Xenon-only unit drop-in example. The required NAS directory has not been provisioned, and effective CIFS ownership/modes, backup, and restore still require verification. Do not enable the target until those checks pass. Do not use Xenon's mounted /nas/Shared root.

Install /etc/solari-notify-failure-HOST.conf as root:root mode 0600 with SOLARI_NOTIFY_PYTHON and SOLARI_NOTIFY_CONFIG for that host. Without Pika or a valid notifier config, delivery is skipped with a local warning; the backup unit still fails as expected.

4. Restore drill

  1. Select a dated artifact and verify the file name, size, ownership, and checksum if one is available. Run gzip -t before import.
  2. Create a new disposable database on an isolated MariaDB instance. Stream the dump into it; do not overwrite the production database during a drill.
  3. Run mariadb-check, compare expected table/view/trigger counts, and exercise application reads against the restored copy.
  4. Record the artifact date, MariaDB version, restore duration, object checks, and any repair. Remove the disposable instance after verification.
  5. For an actual production restore, first preserve the current database and application state, identify an approved recovery point, stop affected writers, restore into a separate database, validate it, and perform a reviewed cutover with a tested rollback. Coordinate Forgejo database and repository-file restores from the same recovery point.
sudo gzip -t /data/backups/sor-YYYY-MM-DD.sql.gz
mariadb --defaults-file=/etc/solari-backup-test.cnf --protocol=tcp -h127.0.0.1 -P3307 -uroot \
  -e 'CREATE DATABASE sor_restore_check'
sudo gzip -dc /data/backups/sor-YYYY-MM-DD.sql.gz | \
  mariadb --defaults-file=/etc/solari-backup-test.cnf --protocol=tcp -h127.0.0.1 -P3307 -uroot sor_restore_check
mariadb-check --defaults-file=/etc/solari-backup-test.cnf --protocol=tcp -h127.0.0.1 -P3307 -uroot --check sor_restore_check

The defaults file must point to a disposable local/test MariaDB instance on port 3307, never the production socket. Replace the sample name only with a newly created scratch database. A production cutover is a separate operational action and is not part of the restore drill.
