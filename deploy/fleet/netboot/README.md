# SolariNet Fleet — netboot & unattended install

> **Security status: do not expose this service to shared networks.** The
> current templates fetch scripts, unattended configs, kernels, and initrds
> without a verified signature chain. F-07 is open; the signed trust contract
> is at [`docs/rework/F07-signed-provisioning-contract.md`](../../../docs/rework/F07-signed-provisioning-contract.md).
> Keep PXE isolated and disabled until its loader, installer, and firstboot
> verification gates pass. A checksum downloaded from this same HTTP server is
> not an authenticity check.

The candidate `deploy/fleet/release_manifest.py` tool can stage and verify
read-only CMS-signed release trees. It is not yet wired into this netboot flow:
the current loader, per-MAC scripts, installer configs, kernels/initrds, and
firstboot artifacts are still not verified end to end. Do not use the manual
override or enable PXE on a shared network while that integration is incomplete.

Netboot-driven, unattended OS installation for x86_64 (BIOS + UEFI) and arm64
machines, plus the shared first-boot agent installer used by every path
(including the Pi image builders under `../pi/`).

The whole tree is rendered per-target and rsync'd to the provisioning host
**`benzene`** (openSUSE, `10.5.2.50`), where nginx serves the HTTP artifacts at
**`http://10.5.2.50:8080/`** and a TFTP server exports the small iPXE binaries.

> Templates here contain `@@PLACEHOLDER@@` tokens. A render step (written by the
> integrator) substitutes them per-target and writes the concrete artifacts into
> the serving tree. See the **token manifest** below for every token.

## Go-live: iPXE loaders + which DHCP advertises them

`build-ipxe-loaders.sh` builds the iPXE loaders **with an embedded chain script**
and installs them into benzene's TFTP root, then stages `solari-tftp.service`
(TFTP-only, no DHCP). Embedding `chain …/boot.ipxe` into the loader is what makes
the **UniFi DHCP** path (Option B) work: UniFi advertises a single boot filename
and does not vary its reply by user-class, so a *stock* iPXE loader would re-request
the same filename forever (a boot loop). The embedded script fetches our HTTP menu
the instant iPXE starts; `|| exit` falls back to local disk for un-staged machines.

```sh
# build + install loaders, stage the TFTP-only service:
deploy/fleet/netboot/build-ipxe-loaders.sh
# ...and go live (enable service + open firewall):
deploy/fleet/netboot/build-ipxe-loaders.sh --enable
```

Then pick ONE DHCP source (they must not both answer PXE):
- **Option A — proxyDHCP on benzene**: `staging/go-live.sh` (does DHCP *and* TFTP,
  with per-arch boot-file selection). Leave `solari-tftp.service` disabled.
- **Option B — UniFi DHCP**: set Network → LAN → DHCP → Network Boot →
  next-server `10.5.2.50`, filename `ipxe-x86_64.efi`; run `solari-tftp.service`
  for the file transfer. UniFi has only one filename field, so the embedded-script
  loaders above are required for BIOS/arm64 clients to reach the menu.

## Boot flow (x86 + arm64 via iPXE)

```
Firmware PXE (BIOS/UEFI)
   │  DHCP: next-server=benzene, filename=undionly.kpxe | ipxe.efi | ipxe-arm64.efi
   ▼
iPXE binary (from TFTP root)
   │  re-DHCP as user-class "iPXE" → handed boot script URL (DHCP opt 67)
   ▼
http://10.5.2.50:8080/ipxe/boot.ipxe          (generated by image-refresh.py)
   │
   ├─ STAGE 1  chain to  ipxe/mac-<mac>.ipxe   (per-MAC staged auto-install?)
   │      • exists  → unattended install of the staged image  → DONE
   │      • 404     → fall through (safe: no staged profile = no wipe)
   │
   ├─ STAGE 2  interactive menu (operator picks a FETCHED image:
   │           distro → release → arch; only images IMAGE_REFRESH verified)
   │      → loads installers/<distro>/<release>/<arch>/{kernel,initrd}
   │      → kernel cmdline points at the rendered unattended config:
   │           Debian    preseed/url=…/configs/<mac>.preseed
   │           Ubuntu    ds=nocloud-net;s=…/configs/ubuntu/<mac>/
   │           openSUSE  autoyast=…/configs/<mac>.xml
   │
   └─ STAGE 3  safe default → boot from local disk (menu timeout / any failure)
```

Every unattended installer runs, in its late/post-install hook,
`installers/solari-firstboot.sh` inside the freshly installed system: it pins the
server in `/etc/hosts`, installs `solariClient`, writes `/etc/solari/client.conf`,
installs+enables the systemd unit, and stages `/etc/solari/PENDING_ENROLLMENT`.

## Images: prov_images → IMAGE_REFRESH → boot menu

The installer images offered at netboot are the SoR's `prov_images` rows with
`boot_method='ipxe'` (Pi-native netboot and write-to-media rows are handled by
`../pi/`, not this menu). Nothing is hardcoded: the row's `source_url` /
`checksum_url` drive the fetch, and the menu lists **only rows that have been
fetched and verified** (`sha256` and `fetched_at` set, not soft-deleted). With
no fetched image the menu offers just the shell, reboot and local disk.

`IMAGE_REFRESH image=<id>` (operator-gated verb) runs
`deploy/fleet/image-refresh.py --image <id> --op <principal>` on xenon:

1. loads the live row; refuses non-`ipxe` rows;
2. downloads the upstream **checksum file** (https only) and resolves the
   expected sha256 of every file it will fetch — refuses if there is no
   checksum source or no entry for a file (never fetches unverified):

   | distro | files served | checksum source |
   |---|---|---|
   | `debian` | `linux`, `initrd.gz` from `source_url` | `checksum_url` (the installer's `SHA256SUMS`, paths `./netboot/debian-installer/amd64/…`) |
   | `ubuntu` | `linux`, `initrd` extracted from `ubuntu-<point>-netboot-<arch>.tar.gz` | `checksum_url` (release `SHA256SUMS`); the tarball name — newest point release of `release_name` — is resolved **from** that file |
   | `opensuse` | `linux`, `initrd` from `source_url` (`…/boot/<arch>/loader/`) | `checksum_url`, or when NULL the repo's `CHECKSUMS` (`source_url` minus `boot/<arch>/loader/`) |

3. runs `deploy/fleet/fetch-images.sh` on benzene (below);
4. records `version`, `sha256`, `fetched_at=NOW()` on the row;
5. regenerates `ipxe/boot.ipxe` from every live fetched iPXE row
   (`netbootlib.render_boot_menu`) and writes it atomically.

> **Real-upstream caveat (observed 2026-10-31):** Ubuntu 24.04's
> `releases.ubuntu.com/24.04/SHA256SUMS` lists only the ISOs, **not** the
> `…-netboot-amd64.tar.gz` tarballs, so a refresh of the seeded Ubuntu row
> refuses ("lists no ubuntu-24.04[.N]-netboot-amd64.tar.gz"). That is the
> intended fail-closed behaviour; serving Ubuntu needs a checksummed source.

### On-disk layout and the sha256 convention

```
installers/<distro>/<release_name>/<arch>        -> .<arch>.v.XXXXXXXX   (symlink)
installers/<distro>/<release_name>/.<arch>.v.XXXXXXXX/
    linux, initrd[.gz]          # the served boot artifacts
    SHA256SUMS.solari           # sha256sum-format manifest of those files
    solari-image.json           # distro/release/arch/version/source_url + manifest_sha256 + fetched_at
```

- `<arch>` is the **prov_images arch** (`x86_64`, `arm64`, …) everywhere on
  disk; distro names (`amd64`, `aarch64`) appear only inside upstream URLs.
- Release-aware, so Debian 12/13 or Leap/Tumbleweed coexist.
- **`prov_images.sha256` = sha256 of that image's `SHA256SUMS.solari`** (one
  CHAR(64) for a multi-file image). `sha256sum -c SHA256SUMS.solari` in the
  image dir re-verifies the served files; `sha256sum SHA256SUMS.solari` must
  equal the SoR value.
- `version` = the upstream point release where the file names carry it
  (Ubuntu, e.g. `24.04.5`), else `fetched-YYYYMMDD` (Debian's `SHA256SUMS` and
  openSUSE's `CHECKSUMS` carry no build/snapshot id).
- The swap is atomic: everything is downloaded + verified into a staging dir
  next to the target, then the `<arch>` symlink is replaced with `rename(2)`.
  A failed or mismatched fetch leaves the previous image untouched. The
  previous version dir is kept after the swap until image-refresh.py has
  updated the SoR row and regenerated `boot.ipxe`; it then commits with
  `fetch-images.sh --prune <new>`, or — if either step failed — restores the
  SoR row and runs `--rollback <previous|-> <new>`, so the OLD image keeps
  serving with a matching menu and row. **nginx must follow symlinks** (the
  default; do not set `disable_symlinks`).
- Every IMAGE_REFRESH is a `prov_runs` row (`mode='refresh'`, `image_id` set,
  `entity_id` NULL) that ends `succeeded` (`installed <version> …`) or
  `failed` (reason + `old image kept` / `rollback FAILED: …`).
- `solari-image.json` lets `fleet-provision.sh` (which has no SoR access)
  render a per-MAC profile with exactly the menu's paths.

`fetch-images.sh` takes everything as validated arguments and has no SoR
access or URL list of its own (run it through image-refresh.py):

```sh
fetch-images.sh --dest installers/<distro>/<release>/<arch> \
                --file <name> <url> <sha256> [--file …] \
                [--extract <tarball> <member> <out>] [--meta <key> <value> …]
```

It runs a fixed remote script with the values as quoted positional arguments
(`curl --fail --location --proto =https,http`, no `| sh`), prints
`manifest-sha256 <hex>`, and under `SOLARI_PROV_LOCAL=1` (the test seam) runs
locally and also accepts `file://` URLs.

### Upstream dependencies at install time

- **openSUSE `install=` points at the UPSTREAM repo** (`source_url` minus
  `boot/<arch>/loader/`, e.g. `https://download.opensuse.org/tumbleweed/repo/oss/`);
  only the kernel + initrd are served from benzene, not a multi-GB mirror.
- **Ubuntu `iso-url=` points at the upstream live-server ISO**
  (`<source_url>ubuntu-<version>-live-server-<arch>.iso`), which the netboot
  initrd downloads (the tarball's own pxelinux config boots the same way).
- Targets installing openSUSE or Ubuntu therefore need **outbound HTTP(S)**
  to those mirrors. Debian's netboot installer also pulls packages from its
  configured mirror (the preseed).

### Trust

Checksum files are fetched over https from the distribution's servers and the
downloaded files must match them. GPG signatures on `SHA256SUMS`/`CHECKSUMS`
are **not** verified yet, so this protects against corruption and mirror
mix-ups, not a compromised upstream; F-07 (above) remains open.

## Per-MAC staging model (dashboard-driven)

To pre-stage a machine for **auto-install on next boot**, `fleet-provision.sh`
(FLEET_PROVISION / PROV_STAGE) renders `ipxe/mac-profile.ipxe.tmpl` through
`netbootlib.py mac-profile` — from the image dir's `solari-image.json`, so the
kernel/initrd paths are the menu's — and writes it to:

```
http/ipxe/mac-<aa-bb-cc-dd-ee-ff>.ipxe      # <mac> = iPXE ${net0/mac:hexhyp}
```

It refuses to stage a per-MAC install for an image that has not been fetched
(`--distro`, `--release <release_name>`, `--arch`; without `--release` it
defaults per distro and warns). `--stack-vars <file>` (a JSON object) is kept
operator-side only, as `PROV_ROOT/profiles/<cfgkey>/stack.json` (0600); stack
vars are never published in the HTTP root. It never overwrites the generated
`ipxe/boot.ipxe`; the repo's static zero-image `ipxe/boot.ipxe`
(`netbootlib.py bootstrap-menu`) is installed only when none exists.

`boot.ipxe` chains to that file **first**. Because a missing file simply 404s and
falls through to the local-disk default, staging is opt-in and a non-staged
machine is **never** wiped.

### One-shot completion (`--run-id`, PROV_STAGE)

PROV_STAGE (`deploy/fleet/prov-stage.py`) stages with `--run-id <prov_runs.id>`
and `--domain`, and keeps the run record + rendered stack vars operator-side at
`PROV_ROOT/runs/reimage-<run>.json` / `.stack.json` (0600). With `--run-id` the
installer profile also:

- writes the run id to the new system as the Ansible local fact
  `/etc/ansible/facts.d/solari_prov.fact` (`{"run_id": N}`);
- authorizes the provisioning host's **control key** (benzene `~/.ssh/id_*.pub`,
  or `FLEET_CONTROL_PUBKEY`) for the admin user next to the operator key;
- records `run_id=N` in `profiles/<cfgkey>/profile.env`.

`deploy/fleet/prov-finish.py` (xenon `solari-prov-finish.timer`, every 2 min)
polls each running reimage run: over SSH from benzene, as the admin user, it
reads the marker. Only when it names **this** run (the new OS is up) does it
remove `ipxe/mac-<cfgkey>.ipxe` + the installer configs (only while
`profile.env` still names this run, under the per-MAC SoR lock that PROV_STAGE
also holds while publishing; it becomes `finished-<run>.env`), install python3
if missing, verify the installed OS family/arch, and run the stack playbook
(check, then apply). Host keys: probes before the marker is seen use a
throw-away known_hosts; the key that first answers with this run's marker is
pinned in `runs/reimage-<run>.known_hosts` and required (strict checking) for
every later probe and step, across ticks. The run then ends `succeeded`, or
`failed` after `SOLARI_PROV_APPLY_ATTEMPTS` (default 3) attempts — each attempt
is recorded before it starts, so a crash still uses it up; the profile is
already gone, so a failed apply never reinstalls. A run whose install is not seen within `SOLARI_PROV_INSTALL_TIMEOUT`
seconds (default 6 h) is `failed` and its profile **disarmed** (moved to
`profiles/<cfgkey>/disarmed-<run>.*`); re-stage to retry.

Reinstall-loop window: until the marker is seen, a machine that network-boots
before its disk (BIOS/PXE-first boot order) re-enters the installer on reboot.
UEFI installers put the installed OS first; for PXE-first machines, watch the
first boot or fix the boot order after the install.

## Directory layout on benzene

```
/srv/solari-provision/netboot/
├── tftp/                                   # TFTP root (small iPXE loaders only)
│   ├── undionly.kpxe                       # BIOS iPXE
│   ├── ipxe.efi / snponly.efi              # x86_64 UEFI iPXE
│   └── ipxe-arm64.efi                      # arm64 UEFI iPXE
└── http/                                   # nginx docroot → http://10.5.2.50:8080/
    ├── ipxe/
    │   ├── boot.ipxe                       # generated from fetched prov_images rows
    │   └── mac-<mac>.ipxe                  # rendered per staged machine
    ├── installers/
    │   ├── debian/<release>/<arch>/{linux,initrd.gz,SHA256SUMS.solari,solari-image.json}
    │   ├── ubuntu/<release>/<arch>/{linux,initrd,SHA256SUMS.solari,solari-image.json}
    │   ├── opensuse/<release>/<arch>/{linux,initrd,SHA256SUMS.solari,solari-image.json}
    │   ├── solari-firstboot.sh             # shared first-boot installer
    │   └── solariClient.<arch>             # agent binaries (x86_64/arm64/arm32)
    └── configs/
        ├── <mac>.preseed                   # Debian
        ├── <mac>.xml                       # openSUSE AutoYaST
        └── ubuntu/<mac>/{user-data,meta-data}   # Ubuntu nocloud (dir datasource)
```

> **Ubuntu needs a directory datasource.** `nocloud-net` fetches both
> `user-data` (rendered from `ubuntu.autoinstall.tmpl`) **and** a `meta-data`
> file (may be minimal but must exist, e.g. `instance-id` + `local-hostname`).
> The render step must write both; an absent `meta-data` hangs the installer.

## Token manifest

Every `@@TOKEN@@` used across the templates, what it means, and an example.
Tokens without a value for a given target are simply left unused by that file.

| Token | Meaning | Example |
|---|---|---|
| `@@HTTP_BASE@@` | nginx base URL for all HTTP artifacts (no trailing slash) | `http://10.5.2.50:8080` |
| `@@HOSTNAME@@` | short hostname of the target | `web-07` |
| `@@FQDN@@` | fully-qualified domain name of the target | `web-07.lan` |
| `@@DOMAIN@@` | DNS domain (Debian/AutoYaST hostname split) | `lan` |
| `@@ADMIN_USER@@` | admin account to create (SSH key, passwordless sudo) | `solari` |
| `@@ADMIN_PWHASH@@` | crypt(3) SHA-512 hash for the admin (and root) account; `*`/`!` to lock password login | `$6$abc$…` |
| `@@SSH_PUBKEY@@` | admin's SSH public key (single line) | `ssh-ed25519 AAAA… ops` |
| `@@CONTROL_PUBKEY@@` | provisioning host's control key (`--run-id` only; empty otherwise) | `ssh-ed25519 AAAA… jason@benzene` |
| `@@AUTHORIZED_KEYS_XML@@` / `@@AUTHORIZED_KEYS_YAML@@` | the admin key(s) as AutoYaST `<listentry>` / autoinstall list lines, one per key | — |
| `@@PROV_RUN_ID@@` | PROV_STAGE run id written to the first-boot marker; empty = no marker | `42` |
| `@@TIMEZONE@@` | IANA timezone | `America/New_York` |
| `@@DISK@@` | **explicit** target install disk (never "first disk") | `/dev/sda` |
| `@@PACKAGES@@` | space-separated installer package set (preseed) | `openssh-server sudo curl` |
| `@@PACKAGES_XML@@` / `@@PACKAGES_YAML@@` | the same set as one AutoYaST `<package>` / autoinstall list line **per name** | — |
| `@@DISTRO@@` | distro family for the per-MAC dispatch | `debian` / `ubuntu` / `opensuse` |
| `@@ARCH@@` | agent-binary arch (`solariClient.<arch>`) | `x86_64` / `arm64` / `arm32` |
| `@@MAC@@` | booting NIC MAC, lowercase hyphen form (`${net0/mac:hexhyp}`) | `aa-bb-cc-dd-ee-ff` |
| `@@SERVER_URL@@` | SolariNet server ingest URL for `client.conf` `primaryUrl` | `tls+tcp://benzene.lan:7701` |
| `@@SERVER_NAME@@` | server hostname pinned in `/etc/hosts` / TLS SAN | `benzene` |
| `@@SERVER_IP@@` | server IP for the `/etc/hosts` pin | `10.5.2.50` |

Notes:
- The installer package set is a minimal **per-family bootstrap** (`fleet-lib.sh`
  `FLEET_BOOTSTRAP_PACKAGES_SUSE` / `_DEB`: SSH server, sudo, curl, CA
  certificates, python3) in that distro's own names. Core arrives afterwards as
  the `core` stack (prov-finish). Only a legacy profile staged without
  `--run-id` on Debian/Ubuntu also appends `FLEET_CORE_PACKAGES`.
- `@@ARCH@@` is the agent-binary suffix (`installers/solariClient.<arch>`,
  client build names `x86_64`/`arm64`/`arm32`; `amd64` is normalized to
  `x86_64`). Installer image dirs use the prov_images arch instead
  (`installers/<distro>/<release>/<arch>/`, `armhf` for 32-bit ARM) and are
  never derived from this token.
- `ipxe/boot.ipxe` and `ipxe/mac-profile.ipxe.tmpl` are **not** rendered by
  `render_template`: `netbootlib.py` renders them, validating every value it
  interpolates (iPXE script is a command language).
- `solari-firstboot.sh` also accepts each token at **runtime** via a
  `SOLARI_<TOKEN>` env var (e.g. `SOLARI_HTTP_BASE`), which is how the Pi
  first-boot service drives the same script without rendering.

## What is immediately usable vs network-config-gated

**Immediately usable (no network changes):**
- Rendering configs from the templates.
- Building Pi images (`../pi/build-pi-image.sh`) and scaffolding Pi 5 netboot
  trees (`../pi/pi5-netboot/`).
- Serving artifacts over HTTP/TFTP from `benzene` once nginx/TFTP are up.
- The first-boot installer + enrollment staging (marker-based).

**Network-config-gated (activated in the later provisioning-network rollout):**
- **proxyDHCP / `next-server` advertisement** (UniFi) that steers PXE clients to
  benzene and hands out the iPXE boot filename / `boot.ipxe` URL. Nothing
  netboots until this is live.
- NFS/DHCP for the Pi 5 diskless root (see `../pi/pi5-netboot/README.md`).

**Integrator-owned (stubs to wire):**
- The **render step** that substitutes `@@TOKEN@@`s and lays out the serving
  tree (including Ubuntu's `meta-data`).
- The **real enrollment call** in `solari-firstboot.sh` (clearly delimited
  `SOLARINET ENROLLMENT HOOK` block) — swap the `PENDING_ENROLLMENT` marker for
  `deploy/enrollment/solari-enroll.sh` with an out-of-band one-time token.
